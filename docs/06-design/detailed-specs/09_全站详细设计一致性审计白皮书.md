## 4. Canonical 契约

### 4.1 ID 与字段

| 语义 | SQL canonical | JSON/API canonical | 主要拥有域 |
|---|---|---|---|
| 用户 | user_id | userId | USR/公共账号 |
| 词汇 | vocab_id | vocabId | VOC |
| 句块 | chunk_id | chunkId | VOC |
| 表达 | expression_id | expressionId | VOC |
| 语法点 | grammar_point_id | grammarPointId | GRM |
| 句子 | sentence_id | sentenceId | GRM/WRT |
| 题目 | question_id | questionId | ASM |
| 练习实例 | exercise_id | exerciseId | ASM |
| 作答 | attempt_id | attemptId | ASM/LST/SPK |
| 会话 | session_id | sessionId | ASM/SOC/SPK |
| 内容版本 | content_version_id | contentVersionId | CMS/各内容域 |
| 请求 | request_id | requestId | 全局中间件 |

SQL 统一 snake_case，REST JSON 统一 camelCase。客户端不得自行传入并覆盖服务端解析出的 userId；所有跨域引用必须带 contentVersionId 或等效版本字段。

### 4.2 响应、幂等、分页和事件

成功包：

~~~text
{ requestId, data, meta }
~~~

错误包：

~~~text
{ requestId, error: { errorCode, message, retryable, details } }
~~~

写操作统一使用 Idempotency-Key；离线事件额外使用 clientEventId + clientSeq。幂等键冲突必须返回 IDEMPOTENCY_CONFLICT，不得把同一 key 的不同 request body 当成新业务。列表统一使用 cursor、nextCursor、hasMore，禁止以页码作为跨版本稳定游标。

事件统一使用 domain.action.vN，至少包含 eventId、schema、occurredAt、actorId、requestId、clientEventId（若来自客户端）、contentVersionId（若涉及内容）和 payload。事件先在本地事务中落 outbox，再投递 RabbitMQ 或 Redis Streams；消费者按 eventId 去重。

### 4.3 学习掌握状态映射

05 的跨域展示状态为 NEW、LEARNING、MASTERED、CONSOLIDATED。02 为满足 SRS 解释力保留更细的内部状态，映射如下：

| VOC 内部 MasteryStatus | 跨域 canonical 状态 | 说明 |
|---|---|---|
| NEW | NEW | 尚未形成有效学习记录 |
| LEARNING | LEARNING | 已接触但未完成长期掌握 |
| SHORT_TERM | LEARNING | 短期记忆阶段 |
| CONSOLIDATING | LEARNING | D1/D7 或后续稳定巩固中 |
| AT_RISK | LEARNING + riskBand=HIGH | 风险标签不是新的跨域状态 |
| MASTERED | MASTERED | 已完成 D7 门槛 |
| CONSOLIDATED | CONSOLIDATED | 后续 SRS 稳定巩固 |
| SUSPENDED | LEARNING + lifecycle=SUSPENDED | 生命周期覆盖，不进入正常排程 |

任何 API 对外只输出 canonical 状态和必要的 riskBand/lifecycle；内部审计保留原始 SRS 状态。

### 4.4 内容审核状态映射

全局 CMS 状态为 DRAFT、IN_REVIEW、APPROVED、PUBLISHED、ARCHIVED。04 的媒体专用 publish_status 中 REVIEWING 等价于 IN_REVIEW；OFFLINE、REVOKED 是发布后的可用性/版权覆盖状态，不得被解释为新的审核阶段。08 是双审状态的权威定义，所有新 CMS 表应优先采用 content_status + availability_status 两列拆分。

## 6. API、权限和安全审计

### 6.1 路由空间

路由按域隔离：/api/v1/learning、/vocab、/grammar、/writing、/listening、/reading、/phonetics、/speaking、/assessment、/exam、/mastery、/gamification、/social、/auth、/user、/sync、/support、/commerce、/admin。跨文档扫描未发现相同方法/路径重复拥有。

### 6.2 权限边界

- 学员读取只允许已发布内容和本人数据；录音、支付订单、发票、家庭成员和同步检查点按 user_id 隔离。
- 内容编辑、初审、终审、发布、财务对账、风控封禁、Flag 修改是互斥权限；作者不能审核自己的版本。
- 录音、支付回调、Apple signed payload、敏感命中和风控档案不进入普通日志或运营导出。
- 账号、支付和内容写操作的失败分支需要稳定 errorCode；自动重试仅适用于明确 retryable=true 的错误。

### 6.3 Phase 1 AI/RTC 红线

01～08 的设计均把 Phase 1 定义为规则化学习。AI 仅作为 Phase 2 独立服务候选；04 明确不提供 ASR、AI 发音评分和 RTC，08 明确不使用生成式 AI 自动审核或生成课程。未来若启用 AI/RTC，必须新增 ADR、输入输出 Schema、promptVersion、超时/重试、双审和隐私评估。

## 7. 性能、弱网和四级画质

### 7.1 统一基线

- 普通 Core API P95 目标 300～500ms；复杂导入、对账、媒体转码和报表生成使用异步 202。
- 失败重试采用指数退避；非幂等 4xx 不自动重试；幂等写操作重复请求返回首次结果。
- 离线队列必须保存 clientEventId、clientSeq、contentVersion 和 hash；恢复时按序提交，冲突返回可合并信息。
- Ultra、High、Medium、Performance 四级能力由 AdaptivePerformanceEngine 控制；Performance 不初始化 WebGL/Three.js/粒子，微信小程序使用 2D 降级。
