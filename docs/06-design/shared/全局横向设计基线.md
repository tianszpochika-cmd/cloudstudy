### 1.2 Phase 1 横向红线

Phase 1 面向 18 岁以上成人和大学生，遵循目标选择 → 规则化练习 → 反馈 → 复习 → 闭环复盘。Phase 1 不启用生成式 AI、LLM、RAG、ASR、AI 评分、实时 AI 对话、数字人、未成年人/K12、家长模式和 AI 生成课程；规则化口语自练、录音回放和脚本化角色扮演不等于 AI 评测。上述口径来自 [requirements/README.md](../../../requirements/README.md)、[MVP 范围](../../../requirements/mvp-scope.md) 和 [Phase-1 冻结基线](../../../requirements/backlog/Phase-1范围冻结与跨文档基线.md)。

Phase 1 的支付能力可以建模 SKU、订单、权益和激活码，但真实微信/支付宝/Apple 收单默认关闭，必须完成资质、沙盒、退款、对账、回滚和审计证据后才能单独开启；该口径已由 [Phase-1 冻结基线](../../../requirements/backlog/Phase-1范围冻结与跨文档基线.md) 和 [ADR-0007](../../10-decisions/0007-phase1-scope-and-development-governance.md) 冻结。

## 2. 横向命名、ID 与版本约定

依据：[详细设计一致性审计白皮书](../detailed-specs/09_全站详细设计一致性审计白皮书.md)、[详细设计索引](../detailed-specs/README.md)、[API 约定](../../05-api/api-conventions.md) 和 [Phase-1 冻结基线](../../../requirements/backlog/Phase-1范围冻结与跨文档基线.md)。

### 2.1 序列化和字段命名

| 层 | 约定 |
|---|---|
| REST/JSON/事件 payload | camelCase |
| MySQL/SQL/迁移 | snake_case |
| 状态枚举、错误码、事件名 | SCREAMING_SNAKE_CASE 或 domain.action.vN，按对应注册表使用；不得使用中文显示文案 |
| OpenAPI 类型 | 由 packages/contracts 单一事实源生成；客户端不得用未经契约校验的裸 any |
| 时间 | 服务端 UTC；API 使用 RFC 3339；媒体时间使用整数毫秒；音频 token 采用左闭右开区间 |

### 2.2 Canonical ID

| 业务对象 | JSON | SQL | 唯一事实源 |
|---|---|---|---|
| 用户 | userId | user_id | USR |
| 词汇 | vocabId | vocab_id | VOC |
| 短语块 | chunkId | chunk_id | VOC |
| 表达 | expressionId | expression_id | VOC |
| 语法点 | grammarPointId | grammar_point_id | GRM |
| 句子 | sentenceId | sentence_id | GRM/WRT |
| 题目 | questionId | question_id | ASM |
| 练习 | exerciseId | exercise_id | ASM |
| 作答尝试 | attemptId | attempt_id | ASM |
| 学习会话 | sessionId | session_id | 所属会话域 |
| 内容版本 | contentVersionId | content_version_id | COM/ADM |
| 请求 | requestId | request_id | API/观测上下文 |

contentVersionId 是跨域内容引用的最小版本粒度。旧文档中出现的 contentVersion、content_version、contentRef.contentVersion 必须在契约边界映射为 contentVersionId；不得为同一版本再创建第二个事实字段。客户端不能提交或覆盖 userId、tenantId、actorId、ownerId 等权限主体字段，服务端从认证上下文和资源所有权校验。

requestId、traceId、eventId、clientEventId 和 Idempotency-Key 语义不同，不能互相替代：

- requestId：一次进入系统的请求上下文标识，用于响应、日志、审计和回放关联。
- traceId：一次分布式链路的标识，沿 Gateway、领域服务、异步任务、消息和审计传播；迁移期也必须覆盖 `core-api`。
- eventId：服务端接受并发布的事件标识，消费者按它去重。
- clientEventId：客户端离线事件的稳定标识，重试时不变。
- Idempotency-Key：写请求结果去重键，不代表业务事实，也不代表事件。

## 3. 统一 API envelope

依据：[API 约定](../../05-api/api-conventions.md)、[详细设计一致性审计白皮书](../detailed-specs/09_全站详细设计一致性审计白皮书.md) 和 [v1 OpenAPI](../../../packages/contracts/openapi/v1/openapi.json)。

### 3.1 成功响应

所有 v1 JSON API 的成功响应统一为：

~~~json
{
  "requestId": "req_01...",
  "data": {},
  "meta": {
    "apiVersion": "v1",
    "schemaVersion": "1.0.0",
    "serverTime": "2026-08-22T00:00:00Z",
    "traceId": "trace_01...",
    "nextCursor": null,
    "hasMore": false
  }
}
~~~

约束：

- requestId、data、meta 必须存在；data 的领域结构由对应 OpenAPI schema 定义。
- meta 必须含 apiVersion、schemaVersion、serverTime、traceId；列表只使用 cursor、nextCursor、hasMore，不使用 page/pageSize 作为跨域分页事实。
- serverTime 是服务端权威时间；客户端时间只作诊断字段，不能决定 SRS、D+1/D+7、权益、注销或过期。
- 异步导入、对账、媒体处理和报告生成可返回 HTTP 202；后续状态通过查询接口或事件回传，仍使用同一 envelope。

### 3.2 错误响应

所有可公开的错误响应统一为：

~~~json
{
  "requestId": "req_01...",
  "traceId": "trace_01...",
  "error": {
    "errorCode": "STABLE_ERROR_CODE",
    "message": "用户可理解的说明",
    "retryable": false,
    "details": {}
  }
}
~~~

约束：

- errorCode 是稳定机器码，message 是可本地化的人类可读说明；客户端按 errorCode 和 retryable 处理，不按 message 分支。
- details 只能包含完成排错所需且通过敏感字段过滤的数据；不得回传 token、密码、JWS、支付凭证、原始音频、私密笔记、完整自由文本或内部堆栈。
- 同一 envelope 只能有 data 或 error 其中之一；错误不得假装返回空 data 成功。
- 400/401/403/404/409/422/429/5xx 的业务语义、retryable 值和错误码必须写入 OpenAPI 与验收证据。

### 3.3 兼容边界

当前 B0 telemetry helper、部分详细域文档和旧测试仍出现顶层 serverTime、error.code、无 meta、errorCode/message 平铺等形态；它们与本节的 v1 目标 envelope 不一致，详见本文冲突 C-01。新设计、新 API 和新测试只能以本节为目标；旧形态只能由兼容适配层接收或转换，不能继续成为新域的示例。

## 4. Idempotency-Key 与重复提交

依据：[v1 OpenAPI](../../../packages/contracts/openapi/v1/openapi.json)、[API 约定](../../05-api/api-conventions.md)、[VOC/SRS 详细设计](../detailed-specs/02_词汇短语与SRS记忆闭环详细设计.md)、[社群与用户基础服务详细设计](../detailed-specs/07_自习室社群与用户基础服务详细设计.md) 和 [全站审计](../detailed-specs/09_全站详细设计一致性审计白皮书.md)。

### 4.1 请求规则

- Header 名称唯一使用 Idempotency-Key；新接口不得使用 X-Idempotency-Key。
- key 是不透明、非敏感、长度 16–128 的客户端生成值；不得把手机号、邮箱、完整业务文本或 access token 放进 key。
- 所有有副作用的 POST、PUT、PATCH、DELETE，以及离线同步、状态提交、奖励入账、订单/权益、内容发布/下线、录音保存和管理操作，都必须带 key。
- GET/HEAD 不要求幂等键。登录刷新、第三方支付回调等例外必须在 OpenAPI 明确声明；回调还必须使用供应商事件号或 JWS 事实去重，不能默认为安全例外。
- 服务端按方法、路由、actorId、tenantId、key 和规范化请求体哈希建立幂等作用域；不同用户或租户不能共享相同业务作用域。

### 4.2 结果和存储

- 同一作用域、同一 key、同一 body hash：返回首次处理的 HTTP 状态和业务结果，不重复写事实、积分、SRS、订单或审计。
- 同一作用域、同一 key、不同 body hash：返回稳定错误码 IDEMPOTENCY_CONFLICT。
- 请求处理中再次到达：返回可重试的处理中结果或查询入口，不能并行执行第二次副作用。
- 默认幂等结果保留窗口至少 24 小时；财务、内容发布、注销和外部回调可更长，但保留周期必须在对应域契约和审计策略中声明。
- 幂等记录必须能关联 requestId、traceId、actorId、tenantId、body hash、首次结果和审计记录；不得把整个敏感请求体原样写入普通日志。

### 4.3 离线和超时

离线事件同时携带 clientEventId、clientSeq、baseCursor 或 baseStateVersion、contentVersionId、payload hash 和 Idempotency-Key。网络超时不代表失败：客户端先查询幂等结果或进入有序本地队列，不得盲目重新生成业务事实。401 只允许一次静默刷新；仅 retryable 的 429/5xx/网络错误按 Retry-After 和域内预算重试，普通 4xx 不自动重试。

## 5. requestId、traceId、correlationId 与观测

依据：[安全与数据边界](../../02-architecture/security-and-data-boundaries.md)、[API 约定](../../05-api/api-conventions.md)、[全站详细设计一致性审计](../detailed-specs/09_全站详细设计一致性审计白皮书.md) 和 [DoD 验收标准](../../../requirements/acceptance-criteria.md)。

- 服务端为每个入口请求生成或校验 requestId；无效、过长、含敏感信息的客户端值必须被替换。requestId 不能承担去重职责。
- W3C traceparent 作为跨服务链路入口；traceId 贯穿 Gateway、IAM、领域服务、AI 编排服务（Phase 2）、异步 worker、消息、WebSocket 和审计关联。迁移期兼容 core-api 也必须透传。HTTP 层按 v1 OpenAPI 返回 traceId；成功在 meta 中，错误按错误 envelope 放在顶层。
- correlationId 用于把一次业务流程的多次请求、事件、重试和人工处理串起来；它不替代 requestId，也不应直接暴露给用户作为安全凭证。
- API、事件、审计和回放记录至少能沿 requestId → traceId → eventId/clientEventId → 领域事实 → 审计记录回溯。
- actorId 表示执行动作的主体；userId 可以在 payload 中表示被操作的用户，但 actorId 与 userId 不得无条件相等。
- 匿名埋点的 actorId、tenantId 可以为空；requestId、traceId、eventId 等技术关联字段仍必须存在。

## 6. 权限、RBAC 与数据访问

依据：[安全与数据边界](../../02-architecture/security-and-data-boundaries.md)、[Phase 1 Admin 设计](../phase-1/uiux-specs/15_Admin_教研_运营后台.md)、[详细设计 07](../detailed-specs/07_自习室社群与用户基础服务详细设计.md)、[详细设计 08](../detailed-specs/08_商业化收单教研CMS与运营中台详细设计.md)。

### 6.1 访问不变量

- 默认拒绝；每次访问同时校验认证、角色/权限、tenant、资源所有权、阶段和内容可用性。
- 学习者只能读取已发布且可用的内容，以及 userId 等于认证主体的个人数据；客户端不能提升角色、租户或 owner。
- Admin 的租户范围不能自动扩大为全平台；跨租户读取必须有明确审计权限和脱敏规则。
- 资源权限与 UI 角色分开：角色授予权限集合，资源范围、阶段、tenant 和实体 owner 再做细化。
- 作者、内容编辑、一审、二审必须保持职责分离；作者不能审核自己的 contentVersion；一审与二审不能由同一人完成同一发布链。
- 内容导出、用户数据导出、退款、补发权益、奖励概率修改、风控封禁、内容发布/下线和注销都必须审计。

### 6.2 基础角色与域权限

安全基线的基础角色如下；域文档中出现的 scope 名称只能作为这些角色的资源动作细化，不能另造一套互相矛盾的主体模型。

| 基础角色 | 默认范围 | 禁止或需要额外授权 |
|---|---|---|
| learner | 本人数据、所属租户内允许的学习资源、已发布内容 | 其他用户学习数据、草稿内容、管理和支付回调 |
| admin | 本租户内运营和管理资源 | 不因 admin 名称自动获得财务、审计、敏感原文权限 |
| content-editor | 内容/媒体编辑、提交、内容导出范围 | 不得访问用户私密数据和支付数据；不能审核自己的版本 |
| finance | 订单、支付、权益的读取和财务操作范围 | 不得修改内容审核或用户学习事实 |
| auditor | 审计读取和导出 | 不得改变业务事实 |
| finance-auditor | finance 与 auditor 的交集 | 仍须满足双人复核和审计要求 |

Admin UI 的超级管理员、教研、内容编辑、一审、二审、运营、客服、财务、技术运维等角色，必须映射为基础角色 + 已注册域 scope，例如 CONTENT_EDIT、CONTENT_REVIEW_L1、CONTENT_REVIEW_L2、COMMERCE_READ、RISK_OPERATOR、FLAG_OWNER、AUDIT_READ；不能仅依靠前端隐藏按钮实现权限。角色映射未正式收敛前，见冲突 C-06 和待 ADR。

### 6.3 权限拒绝的统一表现

前端和 API 都必须区分 loading、empty、error、offline、permissionDenied；403 不能伪装成空数据。隐私、录音、通知、相册、麦克风等设备权限必须在用户动作触发时申请，并提供无权限时的等效学习路径。该状态矩阵来自 [跨端设计系统与基础设施页面规范](../phase-1/uiux-specs/23_跨端设计系统与基础设施页面规范.md) 和 [隐私、下载、同步与异常恢复规范](../phase-1/uiux-specs/14_客服_隐私_下载_同步_异常恢复.md)。

## 7. 状态机命名与跨域状态映射

依据：[Phase-1 冻结基线](../../../requirements/backlog/Phase-1范围冻结与跨文档基线.md)、[全站一致性审计](../detailed-specs/09_全站详细设计一致性审计白皮书.md)、[VOC/SRS 详细设计](../detailed-specs/02_词汇短语与SRS记忆闭环详细设计.md)、[ASM 详细设计](../detailed-specs/05_做题中心模考与掌握闭环详细设计.md) 和 [内容/CMS 详细设计](../detailed-specs/08_商业化收单教研CMS与运营中台详细设计.md)。

### 7.1 命名规则

- 机器状态统一使用大写下划线，例如 IN_REVIEW；显示文案另行本地化。
- 状态字段必须体现语义域，不用一个 status 同时表达审核、可用性、掌握度、同步和支付，例如 contentStatus、availabilityStatus、masteryStatus、syncStatus、orderStatus。
- 每个状态机声明 aggregate、状态字段、起始态、终态、允许转移、发起角色、转移事件、幂等策略和失败恢复；不得用“任意状态可跳转”。
- 事件名使用 domain.action.vN；状态别名只在兼容 mapper 中出现。新增契约不能继续使用已冻结的旧别名。
- UI 的“未开始、进行中、已完成、待复习、需要帮助”是共享显示语义，不覆盖后端域状态；[设计系统](../design-system.md) 的状态文案必须映射到具体域状态。

### 7.2 冻结的跨域状态

| 语义 | 跨域唯一输出 | 域内状态或证据 |
|---|---|---|
| 内容审核生命周期 | DRAFT → IN_REVIEW → APPROVED → PUBLISHED → ARCHIVED | REJECTED、ROLLBACK_PENDING 作为审核结果/动作；不得伪造新主阶段 |
| 内容可用性/权利 | 由 availabilityStatus 表达 AVAILABLE、OFFLINE、REVOKED、DEPRECATED 等 | 与 contentStatus 分离；OFFLINE/REVOKED 不能当审核阶段 |
| 学习掌握 | NEW、LEARNING、MASTERED、CONSOLIDATED | VOC 可有 SHORT_TERM、CONSOLIDATING、AT_RISK、SUSPENDED 等内部态，经 mapper 映射并保留 riskBand/lifecycle |
| 错题验证 | PENDING_RETRY → DELAY_VERIFY_D1 → DELAY_VERIFY_D7 → MASTERED | 需要重开时使用 REOPENED；旧 PENDING_DELAY 等仅兼容映射 |
| 评测会话 | CREATED、IN_PROGRESS、INTERRUPTED、SUBMITTING、COMPLETED、AUTO_SUBMITTED、CANCELLED、EXPIRED | 评测域拥有 session 状态；页面的暂停/恢复显示不得改写 ASM 事实 |
| 权益 | PENDING、ACTIVE、GRACE、EXPIRED、REVOKED | 退款、冻结、人工调整以不可变流水和 audit 表达 |
| 账号删除 | ACTIVE、DELETION_PENDING、CANCELLED、EXECUTING、ANONYMIZED | 7 天冷静期、任务重试和匿名化结果必须可审计 |

跨域只消费表中冻结的 canonical 状态和事件；GRM/WRT 的 UNLEARNED、WEAK、SHORT_TERM_MASTERED、LONG_TERM_MASTERED、AT_RISK 等内部学习状态不能直接冒充 VOC 的四态。涉及新增状态、别名清理或跨域映射变更时，必须更新状态注册表并走待 ADR 的状态治理项。

## 9. 内容版本、审核与可用性

依据：[详细设计 08](../detailed-specs/08_商业化收单教研CMS与运营中台详细设计.md)、[全站一致性审计](../detailed-specs/09_全站详细设计一致性审计白皮书.md)、[Phase 1 内容验收](../../../requirements/acceptance-criteria.md) 和 [详细设计索引](../detailed-specs/README.md)。

- 内容身份稳定，内容版本不可变；修改生成新的 contentVersionId，不在 PUBLISHED 版本上原地编辑。
- contentStatus 只表达审核/发布生命周期；availabilityStatus 表达下线、撤销、版权或媒体可用性。两者必须分栏、分字段、分事件。
- 每个学习题、解释、音频、字幕、报告、尝试、错题、离线包和埋点引用都必须能回溯到 contentVersionId；内容相关事件缺失该字段时只能是明确的非内容事件。
- 发布记录包含作者、审核人、时间、版本、变更摘要、来源/版权、素材引用和回滚目标；回滚改变当前指针，不删除历史版本。
- 学习者只读取 PUBLISHED 且可用版本；管理端预览草稿必须有独立 content scope，不能让草稿穿透到学习端。
- 离线 manifest 固定内容版本、hash、签名/校验、授权、过期时间和清理策略。服务端发现版本撤销或版权失效时，客户端必须进入可解释的 STALE_CONTENT/不可用状态，保留用户未提交学习事件。

媒体文档中的 REVIEWING、OFFLINE、REVOKED，以及游戏资产中的 DEPRECATED，必须按本节映射；对应冲突和映射契约见 C-04、ADR-PENDING-CONTENT-001。

## 10. 业务事件、埋点与消息投递

依据：[安全 telemetry 基线](../../02-architecture/security-and-data-boundaries.md)、[API 约定](../../05-api/api-conventions.md)、[全站一致性审计](../detailed-specs/09_全站详细设计一致性审计白皮书.md)、[VOC/SRS 事件规则](../detailed-specs/02_词汇短语与SRS记忆闭环详细设计.md) 和 [详细设计 08](../detailed-specs/08_商业化收单教研CMS与运营中台详细设计.md)。

### 10.1 共用事件 envelope

新事件统一采用以下语义；字段是否 nullable 由事件注册表声明：

~~~json
{
  "eventId": "evt_01...",
  "eventName": "vocabulary.review.accepted.v1",
  "eventVersion": "1.0.0",
  "schema": "vocabulary.review.accepted",
  "occurredAt": "2026-08-22T00:00:00Z",
  "environment": "production",
  "source": "core-api",
  "requestId": "req_01...",
  "traceId": "trace_01...",
  "correlationId": "corr_01...",
  "actorId": "user_01...",
  "tenantId": "tenant_01...",
  "clientEventId": "client_evt_01...",
  "clientSeq": 42,
  "contentVersionId": "cv_01...",
  "aggregateType": "vocab",
  "aggregateId": "vocab_01...",
  "payload": {}
}
~~~

字段规则：

- eventName 是唯一事件名，格式 domain.action.vN；新契约不用 eventType 代替它。
- eventVersion 表示 schema 演进版本；schema 是稳定的逻辑 schema 名称；不能把 schema 同时当事件名和版本号。
- payload 是唯一业务载荷容器；新事件不用 data、properties、contentVersion 等同义顶层字段。
- eventId 由服务端生成并去重；clientEventId 只在客户端来源事件存在，重试不变；clientSeq 只保证同一用户/设备/聚合对象的客户端顺序。
- actorId、tenantId 对匿名事件可为空；requestId、traceId、eventId、occurredAt、environment、source、eventName、eventVersion、payload 必须可校验。
- 内容相关事件必须有 contentVersionId；业务主体用 aggregateType/aggregateId；不要在 payload 中复制一套身份事实。

### 10.2 可靠投递和消费

- 领域事实与本地 outbox 在同一事务边界内提交，再由 Kafka-compatible Event Bus 投递；RabbitMQ/Redis Streams 仅作为 v1 兼容或局部迁移适配。
- 消费者按 eventId 去重，处理失败进入重试/死信并保留 requestId、traceId、correlationId；未知 schema 不得静默执行副作用。
- 同一事件可被多个投影消费，但只有事实所有者能写入主事实；投影必须可重建、可回放并记录 schema 版本。
- 埋点注册在 packages/telemetry/policies/telemetry-events.json；业务成功、失败、恢复和权限拒绝不能只用前端点击代替。

### 10.3 埋点最小集合与隐私

功能至少覆盖曝光、主 CTA、成功、退出、失败、恢复、重试、权限拒绝、离线排队、同步结果和 Feature Flag 结果。埋点不得包含手机号、邮箱、完整 IP、设备指纹、access token、密码、JWS、支付凭证、原始录音、完整私人笔记、未审核自由文本或完整 AI 输入。ID、requestId、traceId 在导出和分析场景按安全基线哈希或脱敏。

## 11. 审计、回放与操作留痕

依据：[安全与数据边界](../../02-architecture/security-and-data-boundaries.md)、[详细设计 08](../detailed-specs/08_商业化收单教研CMS与运营中台详细设计.md)、[详细设计一致性审计](../detailed-specs/09_全站详细设计一致性审计白皮书.md) 和 [DoD](../../../AGENTS.md)。

审计是不可变的安全证据，不等同于普通 telemetry。敏感操作至少记录：

~~~text
auditId / action / outcome / occurredAt
actorId / tenantId / requestId / traceId / correlationId
resourceType / resourceId / contentVersionId
beforeHash / afterHash / reasonCode / ticketId
source / clientVersion / approvalStage
~~~

约束：

- 审计记录只能追加，不能由业务用户修改或物理删除；删除用户数据时按保留策略匿名化或保留不可逆摘要。
- 内容编辑、审核、发布、下线、回滚、版权处理、奖励概率、风控封禁、订单/支付/退款/权益调整、用户导出和注销必须有审计证据。
- 一审、二审、财务和高风险操作必须记录主体、租户、资源、前后摘要、理由和工单；失败动作也要记录 outcome。
- 普通日志只记录最小排错信息；录音、支付回调/JWS、原始 AI 输入、K12 监护材料和敏感命中不进入普通日志。
- 回放必须能从 requestId/traceId 定位原始请求、幂等记录、事件、领域事实、审计摘要和版本；不能依赖当前内容覆盖历史事实。

## 12. 隐私、数据生命周期与阶段隔离

依据：[requirements/README.md](../../../requirements/README.md)、[MVP 范围](../../../requirements/mvp-scope.md)、[安全与数据边界](../../02-architecture/security-and-data-boundaries.md)、[客服/隐私/下载/同步规范](../phase-1/uiux-specs/14_客服_隐私_下载_同步_异常恢复.md) 和 [Phase-1 冻结基线](../../../requirements/backlog/Phase-1范围冻结与跨文档基线.md)。

### 12.1 Phase 1 数据边界

- 首次注册和关键入口必须完成 18+ 门槛；Phase 1 不建立未成年人、监护人、家长模式或 K12 数据关系。
- 用户隐私中心必须能查看个人资料、学习记录、录音、设备、权限、SDK/隐私说明、StudyRoom 可见性，并提供导出、清除、重置和注销入口。
- 数据导出必须列出字段、时间范围、脱敏方式、创建人、过期时间和下载状态；未知字段丢弃，手机号/邮箱/display/IP 部分遮蔽，密码/token/cookie/raw audio/payment/JWS/private key 直接丢弃。
- 原始录音是个人敏感数据，按短期保留、用户删除和权限撤回处理；普通事件、报告和客服记录只保存必要的结果或不可逆摘要。
- StudyRoom、排行榜和分享海报只使用用户主动选择且已脱敏的数据；不把学习原文、私人笔记或完整录音公开。

### 12.2 Phase 2/3 隔离

| 阶段 | 允许的横向接入 | 必须隔离 |
|---|---|---|
| Phase 1 | 规则测评、规则反馈、非 AI 录音/回放、发布内容、成人学习闭环 | LLM、RAG、ASR、AI 评分、RTC AI 对话、数字人、AI 生成课程、K12、家长、自由文本社交 |
| Phase 2 | 独立 Python 3.11+ FastAPI + LangGraph/LiteLLM 编排；显式 AI API 和结构化 Schema | 不能回写 Phase 1 事实而绕过 owner；每个 AI 能力必须有 promptVersion、输入/输出 schema、超时、重试、降级、双审、安全和隐私审计 |
| Phase 3 | 独立 K12 需求、教材、监护、组织、权限、内容版权和专项合规体系 | 不得通过 Phase 1 注册、默认数据、营销、路由、Feature Flag 或共享用户主体隐式开放 |

Feature Flag 只能控制已获批准的能力，不能把禁止能力藏在关闭的入口后面。关闭 Phase 2/3 能力后，必须回到 Phase 1 的规则化或静态替代路径；任何跨阶段数据共享需另有契约、同意、保留和删除策略。

## 13. 弱网、离线、同步与恢复

依据：[全站一致性审计](../detailed-specs/09_全站详细设计一致性审计白皮书.md)、[VOC/SRS 详细设计](../detailed-specs/02_词汇短语与SRS记忆闭环详细设计.md)、[听说读详细设计](../detailed-specs/04_听说读全模态精练系统详细设计.md)、[社群/用户/基础服务详细设计](../detailed-specs/07_自习室社群与用户基础服务详细设计.md) 和 [客服/隐私/同步规范](../phase-1/uiux-specs/14_客服_隐私_下载_同步_异常恢复.md)。

### 13.1 离线包

- 只缓存已授权、已发布、可用的内容；manifest 固定 contentVersionId、hash/签名、空间配额、授权、过期时间和删除策略。
- 离线包下载、校验、激活、过期和删除使用明确的状态机；内容撤销、版权失效或版本不匹配不能继续作为有效内容提交。
- Performance 档和低配设备仍能完成核心学习、反馈、提交和恢复；重型模块失败不能阻塞学习主链路。

### 13.2 同步队列

同步项至少包含 clientEventId、clientSeq、eventType/eventName、schemaVersion、deviceId、clientOccurredAt、baseCursor 或 baseStateVersion、entityType、entityId、contentVersionId、payload hash 和幂等键。客户端只记录 pending，不把本地结果当作最终事实。

- 同一用户/聚合对象按 clientSeq 有序提交；重试保持 clientEventId、eventId 语义稳定。
- 前台网络/服务器失败按 1、2、4 秒指数退避，默认最多三次；后台预算由域契约声明，不能无限重试。
- 只重试 retryable 错误；普通业务 4xx、权限拒绝、内容过期和版本冲突必须转为可操作状态。
- 冲突默认服务端事实优先；本地未提交事件不得静默丢弃，展示服务端版本、本地事件、时间和差异字段，允许重新编辑或放弃。
- VOC/SRS 的离线学习事件按现有详细设计保留 72 小时窗口；其他域若采用不同窗口必须在自己的契约中声明并进入同步治理 ADR。
- 状态机完成态不能被旧 checkpoint 覆盖；进程重启、token 过期、网络切换、内容撤销和部分提交都必须可恢复。

## 14. 四级画质与性能降级

依据：[AGENTS.md](../../../AGENTS.md)、[跨端性能自适应](../../02-architecture/cross-platform-and-performance-adaptive.md)、[3D 渲染流水线](../../02-architecture/avatar-3d-rendering-pipeline.md)、[跨端设计系统与基础设施页面规范](../phase-1/uiux-specs/23_跨端设计系统与基础设施页面规范.md) 和 [沉浸式前端架构](../immersive-frontend-architecture.md)。

### 14.1 统一画质档

| 画质档 | 允许的视觉/媒体能力 | 不变的功能底线 |
|---|---|---|
| Ultra | 完整 3D、复杂动效、复杂图表、高质量媒体 | 所有学习、反馈、保存、复习和恢复能力 |
| High | 标准动效、轻量 WebGL、音频波形、地图/图表过渡 | 同上 |
| Medium | 2.5D、SVG、简化动画、静态图表、降级媒体 | 同上 |
| Performance | 文本、静态切片、基础音频、2D 反馈；禁止粒子、复杂 canvas、Three/WebGL 重模块和不可关闭自动播放 | 核心学习、判分、反馈、保存、报告入口和无障碍等效操作 |

AdaptivePerformanceEngine 根据设备、网络、用户设置和运行时帧率/内存决定初始档；运行时允许自动降级，不自动升级。动效、声音、触觉和高成本媒体必须能被用户关闭，不能用颜色、动画或音效作为唯一反馈。3D 模块目标为 High+ 30fps；连续低于约 24fps 或出现内存/上下文异常时降级，具体阈值按 [3D 流水线](../../02-architecture/avatar-3d-rendering-pipeline.md) 的设备守则执行。

### 14.2 四个前端项目映射

| 项目 | 编译/运行目标 | 统一共享 | 不能共享或不能承担 |
|---|---|---|---|
| apps/mobile | 移动 H5、iOS、Android、iPad；微信小程序作为后续条件编译输出 | 契约生成类型、API client、领域规则、Token、埋点、国际化 | 不建立 apps/miniapp-wechat 第二套业务页面、状态或 API 适配层 |
| apps/learner-web | PC Web、平板浏览器、PWA 学习工作区；Windows 默认走 Web/PWA | 同上 | 不复制 mobile 的移动 H5 业务页面，不承载后台和官网 |
| apps/admin-web | Vue 3 + Element Plus；教研、审核、运营、商业化、客服、风控、审计 | 同上；按权限读取管理域数据 | 不复用学习者五 Tab 和学习业务导航；高成本 3D 不是后台功能前提 |
| apps/official-site | 品牌、课程介绍、价格、下载、SEO、合规公示 | 品牌 Token、国际化和必要内容版本引用 | 不承载登录后的学习业务、用户学习数据或学习端状态机 |

平台 UI、导航壳和 DOM 可分别实现；共享的是契约、API client、领域规则、设计 Token、埋点和国际化。所有面向学习者的关键路径必须覆盖移动 H5、iOS、Android、iPad、PC/Windows Web/PWA 的响应式和弱网行为；小程序条件编译只作为 mobile 的目标验证。

### 15.2 最小验收矩阵

| 检查面 | 必须验证的事实 | 通过证据 |
|---|---|---|
| 需求追踪 | requirements、feature-matrix、Phase 1 baseline、页面和 API 一一对应 | featureId 追踪表 |
| 契约 | requestId/traceId、success/error envelope、canonical ID、contentVersionId、错误码 | OpenAPI 校验和契约测试 |
| 权限 | 认证、角色、tenant、owner、已发布内容、403 状态 | 正反例 API/页面证据 |
| 状态 | 仅允许注册的状态和转移；终态不可被旧 checkpoint 覆盖 | 状态机测试、迁移/回放记录 |
| 幂等 | 同 key 同 body 重放首结果；同 key 不同 body 返回 IDEMPOTENCY_CONFLICT；并发只产生一次事实 | 并发和超时测试 |
| 版本 | 内容、题目、解释、媒体、尝试、报告和离线包可追溯到版本 | contentVersionId 证据 |
| 事件/审计 | outbox、eventId 去重、requestId/traceId 关联、敏感操作审计 | 消息回放、审计查询和脱敏检查 |
| 隐私 | 录音、导出、清除、注销、设备权限、日志脱敏 | 隐私测试和合成/去标识数据 |
| 弱网 | 断网、超时、重启、401、429、5xx、内容过期、同步冲突和恢复 | 端到端恢复录像/日志 |
| 跨端/画质 | mobile、learner-web、admin-web、official-site 边界；H5/iOS/Android/iPad/Windows；四档画质 | 视口、设备和 AdaptivePerformanceEngine 证据 |
| Phase | Phase 1 关闭 AI/K12 后仍可学习；不存在隐藏入口、默认数据或营销暴露 | 路由、Flag、注册和内容检查 |
| 回滚 | 内容下线/回滚、支付撤销、同步重放、迁移失败可恢复 | rollback runbook 和演练结果 |

验收必须覆盖正常、空、加载、错误、离线、无权限、部分提交和恢复；关键反馈不能只依赖颜色、Toast、动画、声音或客户端时间。DoD 还要求单元、集成、E2E、跨端响应式、四级画质、隐私、AI 失败降级（仅适用于已批准的 AI 阶段）和文档证据。

## 17. 待 ADR 与落地顺序

以下是识别出的待 ADR 项，不在本文件创建 ADR 文件，也不把编号当成已批准决策：

1. ADR-PENDING-API-001：统一 REST/WS/API client 的 envelope、traceId/serverTime 位置、旧响应兼容期、全域 middleware 和错误码注册。
2. ADR-PENDING-IDEMPOTENCY-001：统一 Header、长度、作用域、保留窗口、重放响应、provider callback 例外和旧错误码映射。
3. ADR-PENDING-EVENT-001：统一 eventName/eventVersion/schema/payload、必填观测字段、contentVersionId、schema 类型、outbox、重放、死信和 registry。
4. ADR-PENDING-RBAC-001：原待决议已由 ADR-0010 处理；后续仅需在 `iam-service`/PDP 任务中补齐角色、域 scope、tenant/owner、双人复核和敏感导出的实现验收，不得重新发明权限主线。
5. ADR-PENDING-STATE-001：跨域状态注册表、内部 mapper、旧别名兼容周期、GRAM/SRS/ASM 会话状态和状态事件版本。
6. ADR-PENDING-CONTENT-001：contentVersionId 的全量迁移、contentStatus/availabilityStatus、媒体/游戏状态映射、离线 manifest、版权撤销和回滚指针。
7. ADR-PENDING-SYNC-001：学习与非学习域的离线保留窗口、队列上限、冲突优先级、部分提交、后台重试和跨设备恢复。
8. ADR-PENDING-PHASE-ISOLATION-001：Phase 2 AI 编排与 Phase 3 K12 的独立路由、schema、数据分区、同意、保留、审计、关闭态和跨阶段引用边界。

ADR 输入必须至少包括冲突来源、受影响 feature/API/table/event/终端/数据、兼容与迁移、回滚、测试、隐私、成本、批准人和日期；该要求来自 [Phase-1 冻结基线](../../../requirements/backlog/Phase-1范围冻结与跨文档基线.md) 和 [ADR-0007](../../10-decisions/0007-phase1-scope-and-development-governance.md)。
