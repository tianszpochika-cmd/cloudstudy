## 验证与受控重生成

```powershell
node scripts/audit/verify-full-design-coverage.mjs
node scripts/audit/verify-v2-design-package.mjs
```

`03-PRD原子需求候选清单.md` 与 `04-原子功能设计登记册.md` 是稳定 ID 的冻结快照，日常修改不得自动重生成。只有在产品/架构负责人批准 PRD-ATOM ID 与数量迁移、确认下游引用和回滚方案后，才可运行 `generate-prd-atomic-inventory.mjs`；`generate-design-traceability.mjs` 也只在确认不会覆盖人工冻结说明后受控执行。平时只运行上述验证脚本。验证通过只代表静态追溯完整，不代表 980 条登记行均已具备可实施详细设计或业务代码已实现。

## 文档约定

- `FEAT-*`：已有的规范功能包编号，不随意改名或复用。
- `SUBFEAT-*`：从 PRD 或功能矩阵功能包中展开的原子子功能编号。
- `US-*`：用户故事编号。
- `AC-*`：验收场景编号；原有无编号验收条目需要在追溯矩阵中补充稳定引用。
- `gameCode`、`contentType`、`ruleVersion`：运行时变体，不创建重复功能编号。

## 完成标准

每一个原子需求都必须能够定位到：所属阶段、功能编号、设计章节、页面/路由、API/数据边界、权限/合规、异常恢复、埋点和验收场景。统计冲突、设计冲突和未覆盖项必须单独列出，不得用推测内容填平。登记册中的“已绑定”只代表设计入口已建立，不代表代码、契约、迁移和测试已完成。
