## 3. 必须在开发前关闭的冲突

### 3.1 统计口径冲突（P0）

| 证据 | 当前值 | 影响 | 处理 |
|---|---:|---|---|
| 矩阵顶部 | Phase 1 540 / Phase 2 228 / Phase 3 212 / 980+ | 对外宣称和排期基线 | 产品负责人确认“功能包/原子能力/治理/状态”是否计数 |
| 矩阵域行合计 | 540 / 208 / 182 / 930 | 与顶部 Phase 2/3、总数不一致 | 运行脚本后回写唯一事实源，并保留变更记录 |
| 显式 `FEAT-*` | Phase 1 171 / Phase 2 7 / Phase 3 6 / 184 | 只能证明主功能包，不证明子功能总数 | 不新增虚假编号；确认后再登记正式 `SUBFEAT` |
| PRD 原子提取 | 2,342 证据行 / 2,115 去重语义候选 | 比 980+ 更细，含治理和维度 | 将功能候选与治理约束分层，不直接相加 |

### 3.2 产品规则冲突（P0）

1. **每日时长**：冻结基线/矩阵采用 `5/15/30/45`；PRD §3.1 写 `5/10/20/30+`；用户故事写 5～20 分钟。需要产品选择一套，并同步 onboarding、Quick Practice、通知、报告、埋点和测试。
2. **游戏数量**：PRD 有 6 类核心游戏并在 P1 写 6～8 款；矩阵将部分游戏合并到 22 个 GAM 主功能，设计用 `gameCode` 承载扩展。需要确认首发清单、每款游戏的 P0/P1 和是否计数。
3. **账号合并**：PRD/MVP 要求账号冲突处理；详细设计禁止静默自动合并，要求二次认证、权益/订单/Household/学习记录/回滚和审计。需要确认产品交互和人工客服兜底。
4. **支付开启条件**：PRD 描述多渠道支付，冻结基线和设计要求资质/平台审核/退款/对账完成前默认关闭。需要确认 Phase 1 是否开启真实支付。
5. **社交范围**：Phase 1 只允许系统动态和预设互动；Phase 2 才考虑自由文本 UGC。需要确认产品宣传、官网入口、后台审核和数据策略不越界。

### 3.3 阶段/范围冲突（P1）

- AI2 矩阵范围写到 PRD §33，但 PRD 还存在辩论、RAG、社交升级 §35～§37；已由 AI2 `SUBFEAT` 设计承接，需产品确认是否回写主矩阵。
- K12 矩阵写 62 项但只列 6 个主 FEAT；已由 22 个 `SUBFEAT-K12` 承接，需确认正式编号、权限、事件和合同是否进入单一事实源。
- PRD/旧 UIUX 中存在 Web/H5/App 多套叫法；冻结架构为四个前端项目，H5、iOS、Android、iPad 和小程序均归 `apps/mobile`，PC/PWA 归 `apps/learner-web`。
- Admin Web 与官网的 canonical 路由尚有语义宿主缺口；已在 UIUX 文档中标成缺口，不将未冻结 URL 当成已实现路由。

## 4. 设计签收规则

每个 `PRD-ATOM-*` 只有在下列证据齐全后才能进入“设计签收完成”：

1. 指向一个明确 `FEAT-*`、`SUBFEAT-*` 或治理主题，且没有把选项/状态重复计成业务功能；
2. 详细设计写明目标、前置、主流程、异常、恢复、权限、隐私、内容/版本和跨端降级；
3. UIUX 写明页面/路由、入口、成功/空/加载/错误/离线/权限/恢复状态和 Deep Link；
4. `packages/contracts/` 有 API/事件 Schema 计划，数据所有权和幂等键明确；
5. `requirements/acceptance-criteria.md` 或域内验收表有可执行断言，并能关联测试证据；
6. Phase 2/3 通过独立 Gate；真实数据、模型密钥、未授权教材和儿童隐私不得进入开发夹具或 Git。

当前登记册给出的“业务设计包已绑定”只完成第 1～3 项的设计入口绑定；contracts、migration、测试和签署完成前，不得将其标记为“已实现”。
