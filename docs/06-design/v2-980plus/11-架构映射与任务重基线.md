# v2 设计单元、架构能力与任务重基线

> 本文件只定义 v2 全量设计包进入下一轮开发任务时的映射规则，不新增业务功能；Phase 1 任务还必须绑定 [`phase1-business-operation/`](phase1-business-operation/README.md) 的运行设计，在 dev-redesign 从[R1 卡计划](redesign/dev-plan-R1.md)按[当前进度](redesign/CURRENT-PROGRESS.md)认领；原 [`v2-phase1-rebaseline/`](../../../requirements/backlog/v2-phase1-rebaseline/README.md) 的 `P1R-*` 只保留来源/复用/冻结追溯；`V2-EXT-*` 属于 v2 范围，但在细化签收前不得进入实现。

## 1. 编号分工

| 编号 | 代表什么 | 是否计入 980 | 进入任务前必须有 |
|---|---|---:|---|
| `FEAT-*` | 已登记的业务功能包 | 是 | PRD/Feature Matrix、设计单元、独立验收 |
| `PRD-ATOM-*` / `V2-980-*` | 原子需求证据或 v2 设计单元 | 作为来源/设计证据 | 来源、入口、八态、前端宿主、契约/数据、权限、事件 |
| `ARCH-*` | Gateway、IAM/RBAC、数据 owner、事件、观测、部署等平台能力 | 否 | 架构 owner、依赖、运行/安全/回滚证据 |
| `ACT-P1-*` / `JNY-P1-*` / `PAGE-P1-*` / `RULE-P1-*` / `INT-P1-*` | Phase 1 角色、旅程、页面、规则和业务联调 | 否 | 输入输出、状态、owner、契约、失败恢复和 GAP |
| `E2E-P1-*` | Phase 1 可执行验收旅程 | 否 | 浏览器/API/owner 数据/Outbox/Kafka/审计/恢复 Evidence |

## 2. 每项任务的最小映射卡

```text
Task ID
├─ Source Ref: FEAT / PRD-ATOM / V2-980（V2-EXT 待细化签收不得进入）
├─ Operation Ref: ACT-P1 / JNY-P1 / PAGE-P1 / RULE-P1 / INT-P1 / E2E-P1

├─ Client Host: mobile / learner-web / admin-web / official-site / none
├─ Gateway Operation: external / internal route and API version
├─ Service Owner: target bounded-context service
├─ Data Owner: schema, migration, Redis namespace, object owner
├─ Security Ref: subject/tenant/role/permission/action/owner/phase/rights/consent + TenantScope
├─ Contract Ref: OpenAPI / AsyncAPI / JSON Schema and generated artifacts
├─ State Matrix: success / empty / loading / error / offline / permission / recovery / processing
├─ Event & Idempotency: eventId, clientEventId, Idempotency-Key, outbox, replay
├─ GAP Register: CONTRACT-GAP / EVENT-GAP / IMPLEMENTATION-GAP / EVIDENCE-GAP + owner + 关闭条件
└─ Evidence: unit / contract / integration / E2E / runtime / observability / rollback
```

## 4. 重基线规则

1. 旧 `DEV-*`/B0–B6 台账只保留为历史执行记录；新任务不直接复制旧依赖和“已完成”状态。
2. Platform 0 先建设 Gateway、IAM/RBAC、契约、数据/事件、观测和服务模板，再逐域迁移 `core-api`。
3. 领域任务必须先声明 owner 和契约，再决定服务是否独立部署；目录、README 或静态 policy 不能代替运行证据。
4. Phase 1 年龄 Gate 是 IAM 拒绝规则：不得把儿童账号、家长账号、监护绑定、未成年人支付或 K12 目标登记为 Phase 1 可见功能。
5. `V2-EXT-*` 在 v2 设计 owner、架构负责人和合规负责人完成细化签收前，不得进入开发、发布、默认菜单、埋点注册或数据库迁移，也不得回退到 v1 文档补定义。
6. 内容/题目规则、attempt/判分报告、学习掌握度/复习状态必须分别落在 `content-service`、`assessment-service`、`learning-service`；BFF、工作流和审计服务不得跨域双写。
7. 完成判定必须同时通过 `requirements/acceptance-criteria.md` 的 G/J 条款和 `requirements/backlog/DoD-Gate与证据包规范.md` 的 v2 平台强制 Gate。
8. `admin-ops-service.support` 是 Phase 1 客服工单唯一 owner；`learner-service.privacy` 拥有隐私导出请求/状态/receipt；`iam-service` 拥有账号删除请求、冷静期和主体最终状态。workflow 只编排，各领域 owner 只处理自己的数据。
9. 运行设计标为 `DESIGNED` 只代表业务语义已确定；存在任何 GAP 或缺少当前提交 Evidence 时，不得继承旧台账的“已完成”。

## 5. 旧 B7+ 执行台账与下一轮重基线

[v2 B7+ 代码重塑与交互测试任务基线](../../../requirements/backlog/v2-B7plus-代码重塑与交互测试任务基线.md) 保留了 103 项代码/静态与运行推进记录：

- B7–B14：Platform 0、共享国际化/主题 Token、Gateway/IAM、领域服务抽取、四前端（含官方站）、Phase 1 收敛与代码级逻辑/交互回归；
- B15–B22：只面向 Phase 1 成人产品，从运行环境、Gateway/IAM、领域服务、四端联调、系统测试、安全/灾备、预发布到生产上线；
- F2：Phase 2 AI，只有 `G-P2` 通过后才从“冻结”变为可认领；
- F3：Phase 3 K12/机构，只有 `G-P3` 通过后才从“冻结”变为可认领。

这些 B7+ 状态只作现状与迁移证据，不再直接充当下一台电脑的开发计划。新的 [Phase 1 开发计划重基线](../../../requirements/backlog/v2-phase1-rebaseline/README.md) 已按“先关闭 contract/event GAP → owner 数据与状态机 → 页面与跨端 → `INT-P1-*` 联调 → `E2E-P1-*` Evidence → 发布 Gate”生成 9 个里程碑、108 个 `P1R-*` 任务。B7–B14 的代码完成不替代新计划的 D2–D5 证据；`V2-EXT-*`、F2/F3 仍不得进入 Phase 1 默认路由。
