# v2 架构与设计一致性审核

> 审核日期：2026-08-29
> 审核标识：`AUDIT-V2-20260829`（关联 ADR-0009/0010/0011/0012/0013/0014；ADR-0011 外部 IdP 方案已废弃，当前认证以 ADR-0013 为准）
> 范围：`docs/06-design/v2-980plus/`（含 `phase1-business-operation/`）、目标微服务架构、ADR、追溯/验收/路线图与 Agent 约束。
> 结论：v2 作为新一轮全量业务设计基线是合理的；Phase 1 角色、旅程、页面、学习规则、后台流程、联调和验收已经形成 D1 运行设计，但列出的契约、事件、实现和 Evidence GAP 尚未自动关闭。目标架构只能按 Platform 0 → 逐域抽取落地，当前仓库的 `core-api` 不能被表述为目标微服务已完成。

## 1. 审核口径

本次以 `v2-980plus/` 为**唯一全量业务设计与需求落地基线**。PRD、Feature Matrix 和 PRD-ATOM 保留来源证据、编号、法规边界与统计作用；v1 `detailed-specs/`、旧 `phase-*` 设计和 B0–B6 只用于历史/迁移/术语对照，不能在冲突时覆盖 v2。

技术组合采用 Java 25 LTS、Spring Boot 4.1.x / Spring Framework 7.x 和匹配的 Spring Cloud Gateway 5.x release train 是可行的：Spring Boot 4.1 官方要求 Java 17 起并支持至 Java 26，Java 25 是长期支持版本；实际 patch 版本必须由统一 BOM 和 CI 兼容矩阵锁定，而非由单个服务自行漂移。

## 2. 已修复的设计—架构冲突

| 审核项 | 原风险 | 修复后的约束 |
|---|---|---|
| v1/v2 事实源 | v2 README 和追溯锚点仍把 v1 详细设计称为领域事实源，会使新任务回退到旧单体边界 | 文档治理、生成器、追溯锚点和 Feature Matrix 均改为 v2 优先；v1 仅作历史/迁移参考 |
| 旧设计入口 | `detailed-specs/`、`phase-1/`、`phase-2/`、`phase-3/`、`shared/` 的索引或补充文档仍会把自己表述为当前施工图或基线 | 所有历史入口增加醒目的 v1 历史/迁移标记并链接 v2；追溯生成器只扫描和链接 v2，防止后续生成时回退 |
| Phase 1 年龄边界 | “儿童账号、家长账号、监护人绑定”被自动登记为 Phase 1 的可开发 USR 功能 | 这些行改为 IAM 成人年龄 Gate 的禁止规则：服务端拒绝且不创建儿童/家长/监护/未成年人支付/K12 主体事实 |
| 题目、作答、掌握度 | content、assessment、learning 的事实所有权存在重叠，容易产生双写和题库漂移 | `content-service` 拥有内容/题目/答案规则版本；`assessment-service` 拥有会话、attempt、判分、报告；`learning-service` 拥有计划、SRS、进度、掌握度投影 |
| Gateway/IAM | 先前文案暗示每次请求都同步调用 PDP，并没有把登录协议、JWT 格式和登录体验分层 | IAM 校验账号密码并签发 JWT Bearer（Access Token）；服务 PEP 以 JWT、资源本地事实和版本化策略为热路径，PDP 只处理高风险/动态/安全缓存未命中且 fail closed；JWT profile、刷新/撤销和四端存储遵循 ADR-0013 |
| 多租户 | 只有 tenant 字段要求，未说明 Phase 1/3 策略或 MySQL 的真实能力 | Phase 1 使用服务端派生的 `platform` tenant；Phase 3 采用 `tenant_id` + `TenantScope` + 复合索引/唯一约束与跨租户测试，明确 MySQL 不自动提供行级安全 |
| 事件与部署 | Kafka 的用途和“同部署单元起步”容易导致 RPC 化或分布式单体 | 事件只发布跨服务集成事实、至少一次投递、按聚合 ID 分区；已抽取服务必须独立进程/schema/凭据/发布回滚，共享集群不等于共享运行时 |
| 四前端项目 | INF 的“全项目共享”可能让官网承载登录后的同步/消息业务 | 官网只承载公开状态、下载、合规与统一登录入口；学习同步/消息仍归移动端和 learner-web，admin 仅承载运营通知 |
| 客服与隐私 owner | 工单、导出和账号删除在旧设计中跨 notification/media/workflow/IAM/learner 摇摆 | `admin-ops-service.support` 唯一拥有客服工单；`learner-service.privacy` 拥有隐私导出请求/状态/receipt；`iam-service` 拥有账号删除请求、冷静期和主体最终状态；workflow 只编排各 owner |

## 3. 合理性结论

1. 微服务数量是**目标边界**，不是首日强制部署清单。先独立部署 Gateway 与 IAM，再按 `learner → content → learning/assessment → media → commerce → social/gamification` 逐域抽取，可避免一次性重写和空壳服务。
2. Gateway、IAM、审计、工作流均不能成为领域事实 owner。Gateway 做边界治理；`admin-ops-service` 聚合/发命令；`workflow-service` 编排补偿；`audit-service` 保留不可变审计。
3. 四前端项目保留不同 UI 实现，但共享 OpenAPI/AsyncAPI 生成物、领域规则、Token、埋点、国际化和 Gate。平台复用不等于复制页面或绕过服务权限。
4. Phase 1 只有成人规则化学习；AI、RTC、K12、监护/机构和真实支付渠道继续由阶段 Gate 阻断。任何隐藏入口、前端开关或客户端字段都不能绕过服务端 Gate。

## 4. 仍需在开发前关闭的 Gate

| Gate | 原因 | 进入实现前需要的证据 |
|---|---|---|
| `V2-EXT-*` 细化签收 | 310 个 v2 范围单元尚无独立名称、来源映射和验收，不能直接生成代码任务 | v2 设计 owner、架构、合规三方签收；同步更新 Matrix、合同、测试台账和 CHANGELOG |
| 自有 JWT 认证中心与 JWT profile | 需要锁定 issuer、audience、非对称算法、刷新/撤销和四端存储策略 | ADR-0012/0013：账号密码、JWT/JWKS、轮换/重放、设备撤销、工作负载身份、迁移/回滚、合规和运维责任 |
| 事件平台/密钥/云实现 | Kafka 兼容、KMS/Vault、集群和数据隔离是目标约束，不等于已有部署 | ADR 与容量、安全、灾备、演练和 SLO 证据 |
| 服务抽取宣称 | 当前 `core-api` 是 Java 17/Spring Boot 3 兼容单体 | 每个目标服务的独立进程、schema/凭据、契约、PEP、数据一致性、观测、故障隔离和回滚证据 |
| Phase 1 运行设计 GAP | `DESIGNED` 不能证明 API、事件、页面、服务和运行 Evidence 已闭合 | 按 `CONTRACT-GAP`、`EVENT-GAP`、`IMPLEMENTATION-GAP`、`EVIDENCE-GAP` 建任务并通过对应 `INT-P1-*`、`E2E-P1-*` |

## 5. 审核后的任务入口

每个新任务必须同时绑定 `V2-980/FEAT/PRD-ATOM`、`ACT/JNY/PAGE/RULE/INT/E2E`、`ARCH-*`、前端宿主、Gateway operation、Service/Data Owner、TenantScope/RBAC、OpenAPI/AsyncAPI、迁移、Outbox/幂等、八态、测试和运行/回滚 Evidence。执行只从 [Phase 1 开发计划重基线](../../../requirements/backlog/v2-phase1-rebaseline/README.md) 的 `P1R-*` 台账认领；设计依据见 [Phase 1 业务运行设计包](phase1-business-operation/README.md)、[11-架构映射与任务重基线](11-架构映射与任务重基线.md) 与 [v2 微服务架构](../../02-architecture/v2-microservices-architecture.md)。
