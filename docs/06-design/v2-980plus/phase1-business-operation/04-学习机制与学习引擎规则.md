# Phase 1 学习机制与学习引擎规则

> 规则版本：`P1-LEARNING-RULES-V1`
> SRS 算法版本：`SM2_Q03_V1`
> 适用：18 岁以上学习者；确定性规则；无生成式 AI、ASR/AI 评分或 RTC
> 注意：本文定义目标规则。现有契约或实现不能满足处必须按文末 GAP 关闭，不能用客户端临时逻辑代替。

> M1-011 只冻结 learner 的 profile/target/preferences、target 到 planning input 的版本边界和 first-day read projection；B9 是这些事实的唯一 canonical API 边界，B1 仅为 compatibility adapter。placement manifest/报告/完成事件归 M1-012，`P1_DAILY_PLAN_V1` 算法、SRS 与 mastery 归 M1-013；本文所有该类约束均已形成静态 D2 契约，仍为 `NOT_RUNTIME_VERIFIED`。

## 1. 学习系统回答的五个问题

学习系统每次都必须给学习者可解释地回答：

1. **我为什么学这个？** 来自目标、placement、计划、到期复习、错题或课程选择。
2. **这次要完成什么？** 一个有时间预算、内容版本和完成条件的任务或 Session。
3. **我哪里对、哪里错？** 由版本化答案规则和确定性判分产生即时反馈。
4. **下一次什么时候再学？** 由 SRS、错题修复或 D+1/D+7 规则决定，客户端不猜。
5. **长期是否真的掌握？** 由跨时间、跨题型的可信证据更新 `mastery_projection`，不是当场答对即掌握。

主闭环为：

```text
目标/placement
  → 计划和今日任务
  → 学习 Session
  → attempt/checkpoint/规则反馈
  → SRS 或错题修复
  → D+1/D+7 延迟验证
  → mastery_projection 和报告
  → 下一轮计划
```

## 3. 从目标和 placement 到第一份计划

### 3.1 前置输入

计划生成前必须存在：

- IAM 成人 Gate `PASSED` 和当前必需同意；
- learner 的 `FOUNDATION` / `COLLEGE_CET` / `POSTGRADUATE_ENGLISH` / `WORKPLACE_DAILY` 目标、每日时长 `5/15/30/45`、时区、每周学习日和内容语言；
- assessment 的 placement report，或用户明确选择的“跳过/快速起步”结果；
- learner 有权读取的已发布内容版本；
- `planningRuleVersion=P1_DAILY_PLAN_V1`。历史字符串 `P1_PLAN_V1` 只能作为 compatibility read alias，绝不形成第二个算法版本或第二条计划事实。

缺少 placement 时可以生成保守的入门计划，但必须标记 `baselineConfidence=UNVERIFIED`，不能把用户自选等级包装为测评结论。

`learning-service` 从 learner 的已确认事实构建并拥有 immutable planning input；输入必须 pin `targetId/targetVersion`、`profileVersion`、`preferenceVersion`、IAM 聚合资格引用 `eligibilitySnapshotVersion/eligibilitySnapshotDigest`、内容版本/epoch、闭合的 `ASSESSED | SKIPPED` placement baseline、`planningRuleVersion` 与 digest。`SKIPPED` 只能携带可选的 `USER_SELECTED_NON_AUTHORITATIVE` 起点提示，不能伪装为已测等级。eligibility digest 只引用 IAM 服务端判定的成人 Gate、当前必需同意、Phase/策略版本，不携带或接受客户端 Gate/consent 布尔值。`targetVersion` 是跨域版本键，B9 为兼容保留的 `stateVersion` 必须与其等价，不能形成两套递增计数器。客户端不能提交 tenant、owner、plan、分数或算法结果。

M1-011 只定义 target → planning input → first-day read projection 的边界：`CONTRACT-GAP-ONB-001` 是 API/schema/查询与恢复引用，`EVENT-GAP-ONB-001` 是同一链路的 producer/consumer/binding；二者已按 M1-006 catalog governance 完成 D2 契约签收。M1-012 独占 `CONTRACT-GAP-ONB-002`、`EVENT-GAP-ONB-002` 与 `EVENT-GAP-PLACEMENT-PLAN`；M1-013 独占日计划算法、预算、SRS 与 mastery，不能由 M1-011 的首日投影反向定义或写入。

首日读投影固定为 `NOT_READY/PROCESSING/READY/DEGRADED` 四态；`READY` 的 `taskCount >= 1`、`tasks.minItems >= 1` 及计数一致性由 OpenAPI 和失败关闭 checker 验证，`DEGRADED` 的原因字段唯一命名为 `degradedReason`，不得再引入 `reason` 别名。生成 TypeScript 同步保留必填字段、state discriminator、禁用字段以及可表达的空数组/非空数组基数；`taskCount` 的数值下限和它与 `tasks.length` 的相等关系仍由 wire schema 与服务端校验，不能只凭 TypeScript 宣称完整运行保证。

### 3.2 placement 规则 `P1_PLACEMENT_V1`

1. 测评内容覆盖词汇、基础语法、阅读、听力四个维度；题目和难度来自一个固定的已发布 assessment snapshot。
2. 客户端只提交答案和耗时，不提交正确答案、得分、等级或推荐路径。
3. 每题客观正确得 1，错误/未答得 0；耗时只能用于稳定性说明或同分分析，不能把错误答案变正确。
4. 每个维度分数为 `该维度得分 / 该维度可得分 × 100`。综合分按 assessment manifest 中版本化的 `dimensionWeight` 加权，权重和必须为 100；客户端不硬编码权重。
5. `P1_PLACEMENT_V1` 的参考区间冻结为：`0–39=A1`、`40–59=A2`、`60–74=B1`、`75–84=B2`、`85–92=C1`、`93–100=C2`。
6. 区间只作为语学星内部起点和“参考 CEFR”展示，不宣称官方认证；题量或维度覆盖不足时降低 `confidence`，不得给出伪精确词汇量。
7. 中断恢复继续使用同一 session 和 snapshot；所有题完成后一次性冻结 report。重复提交返回首次耐久结果。
8. 跳过测评只生成 `UNVERIFIED` 起点；用户后续完成 checkpoint 后可重新校准计划，但不覆盖原报告。

M1-012 将该规则冻结为 10 题的静态 D2 manifest：词汇 3、基础语法 3、阅读 2、听力 2，四个维度权重各 25。维度分先以 `ROUND_HALF_UP` 保留 2 位小数，再按权重聚合并以 `ROUND_HALF_UP` 取 0 位整数，最后应用上述等级区间。覆盖率只统计服务端接受的有效题目，与答对率分开：10/10 且四维达到目标为 `HIGH`；覆盖率至少 0.8 且每维至少 1 题为 `MEDIUM`；覆盖率大于 0 但未达到中档为 `LOW`；跳过或零有效覆盖固定为 `UNVERIFIED`。

当前 B25 只保留历史兼容候选，不能作为 manifest、事件或运行证据。canonical `assessment.placement.completed.v1` 只在 assessment-service 首个耐久 result/report 之后发布一次，并以闭合的 `ASSESSED | SKIPPED` 分支表达结果：`SKIPPED` 的 `aggregateScore/referenceLevel` 必须为空、coverage 为 0、confidence 为 `UNVERIFIED`；用户自选起点只能作为 `USER_SELECTED_NON_AUTHORITATIVE` 提示。真实数据库、Outbox、Kafka、consumer 与 Saga 运行仍由 M2-004/005/006 验证，本节只说明 `D2_CONTRACT_READY / NOT_RUNTIME_VERIFIED` 边界。

### 3.3 起点映射

| placement 输出 | 计划动作 |
|---|---|
| 参考等级 | 选择不高于该等级的首个可学节点；保留一次向下回退入口 |
| 维度薄弱点 | 提高相应技能修复和基础内容的优先级，不直接判“不会” |
| 目标 | 选择考试、交流、阅读、写作、听力或口语路径权重 |
| 每日时长 | 决定日预算，不改变难度结论 |
| 权益/版权/阶段 | 只在允许的已发布内容中编排；无权内容必须给免费或可学替代 |

同一 `targetId + contentVersionId + contentEpoch + planningRuleVersion` 只能有一份 active plan。placement 完成事件重复、乱序或重放不得生成第二份计划。

## 4. 学习计划与今日任务编排

### 4.1 计划层级

```text
总目标
  → 月/阶段目标
  → 周目标和 Checkpoint
  → 每日任务
  → 可恢复 Session
```

计划状态为草稿、活动、暂停、完成或取消；改变目标、时区、每日时长、内容 epoch 或阶段 checkpoint 时生成新 plan version，不静默改写历史任务。

### 4.2 今日候选池

服务端按学习者时区和当前 `localDate` 生成候选：

- 未完成且可安全恢复的 Session；
- 已到期的 D+1/D+7 验证；
- 逾期和今日到期的 SRS；
- 待修复错题和近期高频错因；
- 当前目标路径的必修节点与 checkpoint；
- 新词、短语、语法、听力、阅读、口语自练、写作和场景课；
- 用户手动选择的合法课程；
- 可选的学习游戏或受控自习室任务。

只有仍已发布、有权利、有权益且版本可读的内容可以进入候选池。

### 4.3 稳定排序

候选按以下 tuple 排序，前项优先，最后使用稳定 ID 打破同分，保证相同输入可重放：

```text
priorityClass
→ dueAt/expiredAt（越早越先）
→ risk/weakness（越高越先）
→ goalAffinity（越高越先）
→ lastEvidenceAt（越早越先）
→ stable item/task id
```

`priorityClass` 冻结为：

1. `RECOVERY_REQUIRED`：未完成的关键 Session、提交结果待确认；
2. `DELAY_VERIFICATION_DUE`：D+1/D+7 已到期；
3. `SRS_OVERDUE_OR_DUE`：逾期和今日 SRS；
4. `MISTAKE_REPAIR`：待修复或重新打开的错题；
5. `GOAL_CRITICAL`：目标路径必修、checkpoint、考试临近任务；
6. `NEW_CORE`：新内容和技能轮换；
7. `OPTIONAL`：游戏、社交、额外挑战。

用户可重排同一优先级内的非强制任务；不能通过拖拽删除到期验证或伪造完成。延期操作写入原因和新日期。

### 4.4 时间预算

默认预算采用“复习/修复 40% + 目标新内容 40% + 技能轮换 20%”：

| 每日时长 | 复习/修复 | 目标新内容 | 技能轮换 | 说明 |
|---:|---:|---:|---:|---|
| 5 分钟 | 2 分钟 | 2 分钟 | 1 分钟 | 至少一个到期/修复项和一个目标项；无到期项时补目标项 |
| 15 分钟 | 6 分钟 | 6 分钟 | 3 分钟 | 适合首发默认计划 |
| 30 分钟 | 12 分钟 | 12 分钟 | 6 分钟 | 可包含一次较长阅读/听力 |
| 45 分钟 | 18 分钟 | 18 分钟 | 9 分钟 | 可包含 checkpoint 或综合练习 |

规则：

- 任务使用服务端版本化的 `estimatedMinutes`；允许总预算最多向上取整 10%，不能为了填满分钟拆出无意义任务。
- D+1/D+7、逾期 SRS 和高风险错题可把复习比例提高到 70%，相应降低新内容；页面说明“先清理复习积压”。
- 没有复习债务时，空余预算回到目标新内容，再到技能轮换。
- 游戏和社交不占用核心计划的必修预算；它们只能作为完成后的可选出口。
- 学习者调整每日任务量时，服务端生成新 plan version；已完成和已提交事实不回退。

### 4.5 积压保护

当到期复习预计时间超过当天复习预算两倍时进入 `CATCH_UP`：

1. 按逾期天数、遗忘风险、目标相关度和错题频次排序；
2. 给出 2–7 天清理方案和每天上限；
3. 新内容降低到总预算的 0–20%，但保留一个轻量目标项以维持方向感；
4. 不一次性把全部积压显示为必须完成，也不修改历史 dueAt 来伪造“无积压”；
5. 用户可选择正常、快速追赶或分天清理，选择写入 plan version。

### 4.6 推荐解释

每个任务至少返回一个服务端 reason code 和用户文案所需参数，例如：

- `DUE_TODAY`、`OVERDUE_HIGH_RISK`；
- `D1_VERIFICATION`、`D7_VERIFICATION`；
- `RECENT_MISTAKE`、`REPEATED_ERROR_CATEGORY`；
- `GOAL_CET4`、`GOAL_LISTENING`；
- `RESUME_SESSION`、`PLAN_CHECKPOINT`；
- `SKILL_ROTATION`、`CATCH_UP_PROTECTION`。

前端可以本地化文案，但不能自行改变推荐原因或优先级事实。

### 4.7 `P1_DAILY_PLAN_V1` 的 D2 精确编排口径

`config/p1r-learning-loop-contract.v1.json` 是本节的结构化、可机读 policy。它只冻结 D2 合同规则，所有真实 owner 写入、Outbox、Kafka、worker 与浏览器链路仍是 `NOT_RUNTIME_VERIFIED`。

一次 planning run 必须 pin `target/profile/preference` 版本、IANA `timezoneId`、`weeklyStudyDays`、`dailyQuotaMinutes`、IAM eligibility version/digest、content epoch/eligibility digest、闭合 placement baseline、`localDate/asOf`、所有 source watermark/digest、用户拖拽 overlay version 和 candidate snapshot digest。相同的完整 pin 必须得到相同任务序列；不得读取未 pin 的 wall clock、随机数、locale 排序或客户端算法结果。

候选的最低字段为 `candidateId/logicalItemId/actionAggregateId/candidateType/priorityClass/budgetLane/estimatedMinutes/riskScore/goalAffinity/contentPin/sourceFactRefs/eligibilityDecision/primaryReasonCode`。可执行候选同时满足已发布、可读、版权、权益、Phase、成人 Gate 与同意条件；紧急版权/安全下线只给 recovery reference，不能继续给可执行内容任务。普通候选按 `logicalItemId` 去重，恢复 session 按 `sessionId` 去重；同一 item 的 winner 是最低 `priorityClass` 序号，所有被压制候选须保留 `winnerCandidateId/suppressionReason` 审计信息。

唯一稳定排序 tuple 为：

```text
priorityClass.ordinal ASC
→ dueSortAt ASC（无 due 使用 9999-12-31T23:59:59.999999999Z）
→ riskScore DESC
→ goalAffinity DESC
→ lastEvidenceAt ASC（无 evidence 使用 0001-01-01T00:00:00Z）
→ stableCandidateId ASC（canonical ASCII/UTF-8 binary）
```

计划预算固定为下表；`totalCap=ceil(dailyQuotaMinutes×1.10)`，任务只能按服务端版本化 `estimatedMinutes` 整体进入，不能为填分钟拆分。`RECOVERY_REQUIRED` 先在 total cap 内保留；随后 D1/D7、SRS、repair 按稳定排序占 review lane。无复习债务时 review 余量依次回流目标新内容、技能轮换；游戏和社交只属于 optional，不占核心预算。

| 每日时长 | review/repair | goal/new | rotation | total cap |
|---:|---:|---:|---:|---:|
| 5 | 2 | 2 | 1 | 6 |
| 15 | 6 | 6 | 3 | 17 |
| 30 | 12 | 12 | 6 | 33 |
| 45 | 18 | 18 | 9 | 50 |

`debtMinutes` 是当前学习日内 `DELAY_VERIFICATION_DUE + SRS_OVERDUE_OR_DUE` 的 `estimatedMinutes` 之和。只有 `debtMinutes > 2 × normalReviewRepairMinutes`（等号不触发）才进入 `CATCH_UP`。此时 `reviewCap=ceil(quota×0.70)`、`goalCap=ceil(quota×0.20)`、`rotationCap=max(0,totalCap-reviewCap-goalCap)`、`catchUpDays=clamp(ceil(debtMinutes/max(1,reviewCap)),2,7)`。7 天后仍有债务必须返回 `backlogRemainingAfterWindow`，不能伪称清完；没有可完整装入 `goalCap` 的合法轻量任务时返回 `GOAL_LIGHT_ITEM_UNAVAILABLE`。用户的 `NORMAL/FAST/DISTRIBUTED` 选择生成新 plan/overlay version，不能改历史 `dueAt`。

学习者可见 task 至少带 `primaryReasonCode`、排序后的 `secondaryReasonCodes`、安全 `reasonParams`、`planId/planVersion/streamRevision/contentPin/completionRuleVersion`。reason code 只能取结构化 policy 中的闭合集合，例如 `RESUME_SESSION`、`D1_VERIFICATION`、`D7_VERIFICATION`、`DUE_TODAY`、`OVERDUE_HIGH_RISK`、`RECENT_MISTAKE`、`REPEATED_ERROR_CATEGORY`、目标码、`PLAN_CHECKPOINT`、`NEW_CORE`、`SKILL_ROTATION`、`CATCH_UP_PROTECTION`。前端仅本地化文案。

plan 只拥有 task 的 `PLANNED/IN_PROGRESS/COMPLETED/DEFERRED/UNAVAILABLE/CANCELLED` 投影和 session/attempt/report reference；它不得复制 assessment 的 session、attempt 或 report 状态机。session budget 只是 task 的 `estimatedMinutes`，绝不是客户端计时完成权威。拖拽仅限同优先级非强制项；延期只允许 repair/goal/new/optional，必须记录 `deferReasonCode/deferredPresentationLocalDate/overlayVersion`，不得改 SRS 或验证的 canonical dueAt。

## 5. 学习 Session、checkpoint 和完成

### 5.1 创建

进入任务时，`assessment-service` 服务端创建 session，并固定：`planId/taskId + contentVersionId + contentEpoch + snapshotId/snapshotHash + item/question IDs + answerRuleSetVersion + 每题 answerRuleVersion/ruleDigest + sessionType + completionRuleVersion`。题目、答案规则和评分材料来自 `content-service` 的受保护 snapshot；客户端只收到完成交互所需内容，不能提交 tenant、owner、答案规则或评分结论作为权威输入。

Session 持久化状态固定为 `CREATED/IN_PROGRESS/INTERRUPTED/SUBMITTING/COMPLETED/AUTO_SUBMITTED/CANCELLED/EXPIRED`。Attempt 和报告使用独立状态机，不得把“已提交、判分中、报告生成中”混入 session 状态。

### 5.2 运行

- 提交前的作答、标记、播放进度、草稿和题间进度按题或时间阈值保存到 session-scoped checkpoint；canonical 入口是 `putB10AssessmentSessionCheckpoint`，不要求事先存在 attemptId；
- checkpoint 请求携带受保护草稿、`baseStateVersion/checkpointVersion/clientEventId/clientSeq/checkpointDigest`。同版本同摘要返回首次结果；旧版本、同版本异摘要、过期 base version 或终态写入统一失败关闭为 `409`；
- 中断后继续同一 session，不能用“重新开始”掩盖恢复缺失；
- 内容发布新版本不改变进行中的 snapshot；紧急版权/安全下线可以终止新访问并提供替代。

### 5.3 提交和判分

1. 提交必须有 Idempotency-Key 和客户端生成的 `submissionId/submissionDigest`；`attemptId/attemptVersion` 由服务端生成并与首次耐久结果绑定。同键同摘要返回该结果，同键异摘要返回 `409`。
2. `assessment-service` 使用 session 开始时固定的规则集和每题 `answerRuleVersion/ruleDigest` 确定性判分。客观结果同时返回 `objectiveNumerator/objectiveDenominator/scoreBucket/errorCategory/reasonTrace/outcomeDigest`；答案密钥、原始作答和规则正文不进入普通响应、事件、日志或 analytics。
3. 重复提交返回同一 attempt/report；不得重复判分，也不得重复推进任务、奖励或 mastery。
4. 客观题可即时反馈；模考在交卷前可以隐藏得分。
5. 规则无法处理的 Phase 1 主观输入只能给规则比对、参考答案和自评，不伪装为 AI 评分。
6. Phase 1 不生成权威“作弊”结论。历史切屏/失焦数据最多作为非权威兼容候选，不得影响分数、奖励、封禁或报告事实。

### 5.4 任务完成

任务只有满足自身版本化完成规则才完成，例如：

- SRS：本批次所有必需 review 已被服务端接受；
- 课程：规定学习项和练习已完成；
- 阅读/听力：有效进度和必需测验已完成；
- checkpoint/模考：已正式提交并生成结果；
- 口语自练：完成示范、录音/回放或明确选择无录音替代；
- 写作：草稿保存并完成规则反馈/自评步骤。

仅打开页面、播放几秒、客户端计时结束或关闭窗口不能自动记为完成。

## 6. SRS `SM2_Q03_V1`

### 6.1 适用对象和用户输入

单词、短语/句块及经评审允许的结构化 LearningItem 使用同一算法解释器，但每个 item 有独立 `lrn_srs_state`。用户四级输入：

| rawQuality | 用户文案 | 含义 |
|---:|---|---|
| 0 | 完全忘了 | 未能回忆，或未作答就揭晓 |
| 1 | 模糊 | 回忆错误/不完整，揭晓后仅有熟悉感 |
| 2 | 顺利想起 | 正确但需要努力，或存在“猜对”信号 |
| 3 | 轻而易举 | 正确、流畅且信心确定 |

客观结果优先约束信心：`UNANSWERED/REVEALED_BEFORE_ANSWER → 0`，`INCORRECT → min(rawQuality,1)`，`GUESSED → min(rawQuality,2)`，`CORRECT_VERIFIED → rawQuality`。`NO_OBJECTIVE_EXPECTED` 只能由服务端预先声明的合法练习类型使用，仍只取 rawQuality；它不是客户端规避客观判分的开关。客户端不能提交 objective outcome，也不能把错误答案报为 3。M1-013 已在 `assessment.item.assessed.v2` 中冻结服务端 `objectivePolicyPin` 及七个 outcome 分支：非 `NO_OBJECTIVE_EXPECTED` 只能绑定 `OBJECTIVE_ASSESSMENT`，无客观答案的练习只能绑定三种明确的 self-rating 类型；这是 D2 契约闭合，不代表 assessment/learning 运行链路已经验证。

### 6.2 公式

设有效质量为 `q ∈ {0,1,2,3}`，当前 Ease Factor 为 `EF`：

```text
distance = 3 - q
EF' = clamp(round2(EF + 0.10 - distance × (0.08 + distance × 0.02)), 1.30, 2.50)
```

所有公式使用 decimal，不允许 binary float；`round2` 和后文 `round` 均为 `ROUND_HALF_UP`。因此 `q=0/1/2/3` 对 EF 的未 clamp 增量分别是 `-0.32/-0.14/0/+0.10`。每次 formula input/output、rounding mode、前后 EF/interval/repetitions/lapse 都必须成为 review fact 的审计字段。

新状态初始值：`stage=NEW, EF=2.50, repetitions=0, intervalDays=0, lapseCount=0, dueAt=now`。

```text
若 q < 2：
  repetitions' = 0
  intervalDays' = 1
  lapseCount' = lapseCount + 1

若 q >= 2：
  repetitions' = repetitions + 1
  repetitions 1..6 的 intervalDays = [1, 3, 7, 15, 30, 90]
  repetitions > 6：intervalDays' = clamp(round(intervalDays × EF'), 1, 365)
```

`reviewedAt` 是服务端接受 review 的 UTC Instant，不能以客户端时钟驱动公式。`dueAt` 使用服务端派生的 IANA 学习者时区：先令 `reviewedLocal=reviewedAt.atZone(scheduleTimezoneId)`，再以 `reviewedLocal.plusCalendarDays(intervalDays)` 取得 due local datetime，最后保存其 UTC Instant。DST gap 固定前移到第一个合法 local time，DST overlap 固定选较早 offset；每条事实保存 `reviewedLocalDate/scheduleTimezoneId/dueLocalDate/dueAt/timePolicyVersion`。时区改变不得改写已有 `dueAt`，只影响之后被服务端接受的新 review。每次结果保存 `algorithmVersion=SM2_Q03_V1`、前后 state version 和 reviewedAt。

### 6.3 SRS 阶段

```text
NEW → LEARNING → MASTERED → CONSOLIDATED
          ↑          │           │
          └──────────┴───────────┘  q < 2 或失效证据时回到 LEARNING
```

- `MASTERED`：至少 `repetitions>=4 && intervalDays>=30`；
- `CONSOLIDATED`：至少 `repetitions>=6 && intervalDays>=90`；
- `q<2`：进入/回到 `LEARNING`；
- 非法跳转、旧 stateVersion、倒序 reviewedAt、不同 content pin 一律拒绝。

SRS 阶段只描述记忆排程，不等同于错题 D+1/D+7 工作流或全局 mastery projection。

### 6.4 早期和额外练习

dueAt 之前的额外练习可以记录普通 attempt 和练习反馈，但默认不推进 SRS 排程。`SM2_Q03_V1` 对提前复习固定 fail closed：`serverAcceptedAt < dueAt` 返回 `409 EARLY_REVIEW_NOT_ALLOWED`，不得通过频繁点击刷高间隔。后续若批准提前复习，必须新建算法/规则版本和回放迁移，不能放宽本版本。

### 6.5 唯一 SRS 写入口、离线重放和历史 adapter

唯一公开写入口冻结为 learning-service 的 `completeB10LearningReview`（`/api/v1/learning/review-queue/{queueItemId}/complete`）。canonical command 的最低输入为 `baseStateVersion/clientEventId/clientSeq/contentPin/payloadHash/sourceAssessmentAttemptId/rawQuality`；`clientOccurredAt` 只能辅助审计与离线诊断，不能参与 SM2 数学。`contentPin` 至少能证明 `contentVersionId/contentEpoch/snapshotId/snapshotHash`。

客户端必须被拒绝的字段包括 tenant/principal/owner、objective outcome、effectiveQuality、score、mastery、SRS stage、EF、interval、dueAt、algorithmVersion 和 `PASS/FAIL`。客观 outcome 只能来自 assessment result 或服务端受保护 review interaction；公开命令和可信 assessment event 都必须进入同一个 learning review transition service/receipt ledger，不能形成第二个算法或第二次 `lrn_srs_state` 写入。

离线 review 必带 `clientEventId/clientSeq/baseStateVersion/contentVersionId/payloadHash`。同一 `(principal, deviceRegistration, clientEventId)` 同 hash 重放首个 receipt，不同 hash 返回 409；旧 base state、倒序 seq、倒序 reviewedAt、content pin 冲突、终态 queue、算法不符和不可信 outcome 均失败关闭，并返回当前安全 state 或 recovery reference。客户端永不生产 canonical Kafka 事实。

`submitReviewEvent`、`syncReviewEvents` 和发现到的 B1 SRS 写入口全部为 deprecated adapter-only。adapter 只能逐项、有序地翻译到上述 transition service，不能计算 SM2、不能双写 `lrn_srs_state`；缺 `clientSeq/payloadHash/full content pin/可信 outcome` 的历史请求必须拒绝或进入人工恢复。历史 `effectiveQuality=4|5` 不得 clamp 成 Q03。旧写入口只有在未来 runtime gate 后才可返回 410。

## 7. 错题修复、D+1/D+7 和掌握度

### 7.1 三类状态必须分离

| 状态体系 | owner | 允许值/语义 |
|---|---|---|
| SRS stage | learning | `NEW/LEARNING/MASTERED/CONSOLIDATED` |
| 修复/验证工作流 | assessment 结果 + learning 调度 | `REVIEW_QUEUE/LEARNING/DELAY_VERIFY_D1/DELAY_VERIFY_D7/MASTERED/REOPENED` |
| 全局 mastery projection | learning | `NEW/LEARNING/MASTERED/CONSOLIDATED`，带 score/evidence/version |

页面可以把它们合并成易懂文案，但数据模型、事件和规则不能复用同一个字段。

### 7.2 错题产生

客观错误、未答、规则化低质量结果或延迟验证失败由 assessment 记录 attempt 和 error category，再发布可信已评分事实。canonical 语义错因闭合为 `KNOWLEDGE_GAP/MEMORY_FUZZY/CONFUSABLE/RULE_CONCEPT/LISTENING_DISCRIMINATION/READING_COMPREHENSION/SPELLING_OR_STRUCTURE/CARELESS_OR_OMISSION/TIME_INSUFFICIENT/UNCLASSIFIED`。B10 的 `CHOICE/MATCHING/ORDERING/...` 是题型或规则失败分类，不能直接替代上述语义错因；必须以版本化 assessment mapping 产生。用户“其他”只能作为非权威备注，不能成为事实。

learning 消费事件后按 `sourceAssessmentEventId + itemId + projectionVersion` 幂等生成/更新修复项；原题、用户答案、规则、来源、内容版本、首次/最近错误、次数和下次验证均可追溯。

### 7.3 修复流程

```text
错误 → REVIEW_QUEUE
  → 规则/证据回顾
  → LEARNING（变式练习）
  → 当场修复通过
  → DELAY_VERIFY_D1
  → D+1 通过
  → DELAY_VERIFY_D7
  → D+7 通过
  → MASTERED
```

- 主要修复题必须是同一 LearningItem/规则的合法变式或不同情境，不以重复原题作为唯一策略。每次选择必须保存 `variantSelectionRuleVersion/variantCatalogDigest/sourceQuestionId/variantId/relationship/contentPin`；relationship 仅允许 `LEGAL_VARIANT/CONTEXTUAL_EQUIVALENT`，tie-break 固定为 `contentVariantRank ASC → variantId ASC`。
- 当场修复必须由 assessment 的版本化规则判定；自评只作辅助信号。
- D+1 固定为 immediate repair local date 之后的第一个 configured study day；D+7 nominal date 固定为 D1 PASS local date 加 7 个日历日，scheduled date 为该日或之后第一个 configured study day。两者保留 `nominalDueLocalDate/scheduledDueLocalDate/dueAt/timezoneId/weeklyStudyDays`，本地时间和 DST 决议复用 SM2 policy。
- 任一延迟验证失败进入 `REOPENED`，随后回到修复队列并调整相关 SRS 风险；不能自动判通过。
- 内容已下线时优先使用同一知识点的已发布替代；没有替代则保留历史证据并以独立 `repairAvailability=WAITING_FOR_CONTENT` 标记等待内容，不丢失错误事实或混入 repair workflow state。

### 7.4 mastery projection

每条可信 evidence 至少包含：`evidenceId/sourceEventId/attemptId/logicalItemId/contentVersionId/contentEpoch/objectiveCorrect/evidenceScore/objectiveOutcome/effectiveQuality/guessSignal/errorCategory/ruleVersion/ruleDigest/verificationStage/occurredAt/localDate/evidenceDigest`。`evidenceScore=ROUND_HALF_UP(100×objectiveNumerator/objectiveDenominator,2)`；projection 按 evidenceId 去重，除 content-service 已声明的版本化合法替代外不能接受更旧的 contentVersion。

Phase 1 的晋级规则：

- 无 evidence：`NEW`；
- 有学习/作答 evidence 但未完成 D+7 gate：`LEARNING`；
- qualifying evidence 必须是未撤销的客观正确结果且 `effectiveQuality>=2`；同一 localDate 仅取 `occurredAt → evidenceId` 最新一条。当前 mastery epoch 从最近一次 content rule 标记的 `masteryCritical` 错误或 D1/D7 fail 后开始，取当前 epoch 最近三个不同 localDate 的 qualifying evidence，`aggregateScore=ROUND_HALF_UP(sum(evidenceScore)/3,2)`；
- `MASTERED`：当前 epoch D+7 PASS、至少 3 条上述分隔 evidence、`aggregateScore>=85`；
- `CONSOLIDATED`：满足 MASTERED、`aggregateScore>=95`，且最新 qualifying evidence 为 `effectiveQuality=3 && guessSignal=false`；
- 任何新的关键错误或 D+1/D+7 失败立即降到 `LEARNING` 并保留 reasonTrace。D7 assessment PASS 但 mastery gate 未满足时不得进入 repair `MASTERED`，而是 `REOPENED → REVIEW_QUEUE`，reason=`MASTERY_GATE_NOT_MET`。

现有 `MasteryStage.from` 在没有 D+7 时也可能凭分数进入 `MASTERED`，与本规则不完全一致，必须标 `IMPLEMENTATION-GAP-MASTERY-D7` 并在新任务中修正/迁移。

## 9. 报告规则

### 9.1 数据水位

报告只聚合已接受的 owner 事实，并记录 `asOf、sourceWatermark、reportRuleVersion、content/rule/algorithm versions`。事件延迟时标明“数据更新中”，不把缺失值当 0。

M1-010 的 assessment report 只固定单次判分快照：它绑定 session/attempt/submission、内容与答案规则 pin、`assessmentVersion/reportVersion/reportRuleVersion/asOf/assessmentFactWatermark`。日报、周报、阶段报告与 mastery/SRS 水位属于 `learning-service` 后续聚合，不能由 assessment report 直接宣称。

### 9.2 指标

| 指标 | 计算口径 | 来源 owner |
|---|---|---|
| 学习分钟 | 有效 Session 区间按服务端开始/心跳/完成校验后求和；切后台空转和异常超长需截断 | learning/assessment/media 的可信会话事实 |
| 任务完成率 | 已完成必需任务 / 当期已发布且有效的必需任务 | learning plan/task |
| 正确率 | 已评分客观 attempt 的正确项 / 已评分项；未评分和撤销项排除 | assessment |
| 新学/复习数量 | 当期首次接受学习事实 / 接受的 SRS review | learning |
| 错题新增/修复 | 新 mistake 数 / 完成相应验证阶段的修复数 | assessment + learning projection |
| D+1/D+7 通过率 | 对应阶段通过数 / 已完成验证数；未到期不进入分母 | assessment result + learning schedule |
| 掌握新增 | projection 首次进入 MASTERED/CONSOLIDATED 的去重 item 数 | learning |
| XP/Streak | gamification 不可变账本；不能反推学习事实 | gamification |

日报按学习者 localDate，周报按 ISO 周或用户配置周起始日但必须固定在 report snapshot；阶段报告按 plan/checkpoint 边界。任何比例同时返回分子、分母和数据水位。

### 9.3 报告出口

报告必须能回到来源任务、attempt、错因和推荐修复；管理员只读脱敏聚合，不默认读取个人答案或录音。报告不能作为官方 CEFR 认证、医学记忆预测或 AI 诊断。

### 9.4 `P1_REPORT_V1` 精确 snapshot、水位和迟到重建

report key 固定为 `learnerId + reportKind(DAILY|WEEKLY|PHASE) + windowStartInclusive + windowEndExclusive + timezoneId + weekStartRule/planCheckpointBoundary`。每个 snapshot 必有 `reportId/reportVersion/reportRuleVersion/asOf/window/sourceWatermarks/sourceWatermarkDigest/inputVersions/metricDefinitionsVersion/sourceFactDigest/status`。`asOf` 是生成 instant，`sourceWatermarks` 是 owner accepted-fact 高水位；缺少 learning 或 assessment 所需水位时状态必须为 `PROCESSING`，相关 metric 为 `null`，绝不能显示为 0。

`TASK_COMPLETION_RATE` 的分子是 accepted completed required task instance，分母是当期 published 且 effective 的 required task instance（只有留痕的 cancelled/unavailable 才排除）。`OBJECTIVE_ACCURACY` 必须汇总同一集合内的 `objectiveNumerator/objectiveDenominator`，不能平均百分比。`D1_PASS_RATE/D7_PASS_RATE` 的分母只包括相应 stage 已完成的 `PASSED|FAILED` verification，未到期和未完成不进入分母。`NEW_LEARNING_COUNT/REVIEW_COUNT/NEW_MISTAKE_COUNT/FULLY_REPAIRED_COUNT/NEW_MASTERY_COUNT` 均为 policy 定义的去重 count；无分母。任何分母为 0 的比例为 `NOT_APPLICABLE + null`。

学习分钟只能汇总 owner accepted 的 `creditedSeconds/60`；`creditedSeconds` 必须由版本化 `P1_SESSION_V1` 的服务端 activity policy 产生，不能由客户端时长、页面打开或 report 临时估算产生。

迟到事实按 owner `occurredAt/assessedAt` 归属窗口。若该事实 source position 晚于已生成 snapshot 的 watermark，则记录 late event，绝不改写旧 snapshot；同 report key 新建 `reportVersion+1`，填写 `supersedesReportVersion`、新的 watermark/digest 和 rebuild reason。重放按 source event/evidence id 去重，历史事实仍按其 pin 的 content/rule/algorithm 解释。

## 10. 重排、时区、离线和幂等

- 改目标、每日时长或学习日：生成新 plan version，未完成任务重排；已完成事实不移动。
- 跨时区：已保存 dueAt 保持 UTC 事实；显示和下一轮计划使用新时区，防止同一学习日重复 Streak/任务。
- 离线：内容必须已授权下载；review/attempt 用 `clientEventId/clientSeq/baseStateVersion/contentVersionId/payloadHash` 有序补传；服务器才决定评分、SRS、repair、mastery 和完成。同 event 同 hash 回放首次 receipt，异 hash 409；冲突返回安全 state/recovery reference，绝不 last-write-wins 或由客户端合并 mastery/XP/权益。
- 所有写操作使用 Idempotency-Key；同键不同 payload 返回冲突，同键同 payload 返回首次耐久结果。
- 内容版本失效：进行中的合法 snapshot 按安全策略完成；新任务只用当前已发布版本。紧急版权/安全下线优先阻断。
- 算法升级：新 `algorithmVersion` 必须有迁移/回放/对照测试，旧事件仍用旧解释器；Phase 1 不并行启用 FSRS。
