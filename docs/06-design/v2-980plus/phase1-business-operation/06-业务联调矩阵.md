本矩阵把 Phase 1 的跨服务衔接登记为 `INT-P1-*`。它只定义**应被联调和验证的目标关系**：一个事实仍只由一个领域服务写入，跨域只使用已签收的 REST/internal API 或 Kafka + transactional Outbox 事实事件。矩阵中的“目标 consumer”不是“已有订阅/代码已运行”的声明；没有契约、topic、订阅、迁移和真实证据时，必须使用对应的 `CONTRACT-GAP`、`EVENT-GAP`、`IMPLEMENTATION-GAP`、`EVIDENCE-GAP` 或 `UNVERIFIED`。

## 1. Canonical 联调约束

### 1.1 每一条联调都必须满足

1. 外部请求统一经过 Gateway 的 `/api/v1`；Gateway 注入 `requestId`/`traceId`、预校验 JWT，但下游领域服务仍独立验签并执行服务侧 PEP。任何客户端角色、tenant、owner 或积分字段均不可信。
2. 写入由事实 owner 在自身 schema 内完成，并与 Outbox 同事务。Kafka 是至少一次投递；按照 `aggregateId` 分区，消费方按 `eventId`/业务去重键处理乱序、重试、DLQ 与回放。禁止跨服务 SQL、共享表写入、Kafka RPC 和两阶段提交。
3. 事件 envelope 至少保留 catalog 要求的 `eventId`、`eventName`、`traceId`、`requestId`、`schemaVersion`、`aggregateType`、`aggregateId`、`dedupeKey` 和脱敏 payload。Token、密码、支付回调原文、答案规则值、原始音频和未脱敏自由文本不得进入事件。
4. 同一个业务动作的客户端重试以 `Idempotency-Key` 和业务版本保护；离线写入另带 `clientEventId`、`clientSeq`、`baseCursor` 或 `baseStateVersion`。消费者不得依据 UI 数值重新计算奖励、权益或掌握度。
5. 当前本机验收治理仍以 B28/B36 的 `LOCAL-TEST-NO-PASS` 为准；因此本文件的测试证据栏写的是**最低必需证据**，不是通过结论。

### 1.2 事件命名收敛规则

`packages/contracts/events/v1/catalog.json` 是事件名、版本、payload schema、aggregate key 和兼容性规则的执行事实源。v2 域设计中存在不少“业务动作名”，其中有些不是 catalog 的 canonical 事件，另一些只是 UI 浏览行为。新的集成实现应按下表收敛，不得同时发布同义事件。

| v2 设计中的动作名 | catalog canonical 名／处理 | 结论 |
|---|---|---|
| `onboarding.goal_selected.v1` | `learner.target.updated.v1` | 目标事实已经有 canonical 事件；以 `targetId/targetVersion` 去重。 |
| `onboarding.assessment_completed.v1` | `EVENT-GAP-ONB-001` | 没有明确 placement 完成的 canonical 集成事件；不能擅自借用普通 attempt 事件而不定义 payload、consumer 和补偿。 |

| `srs.review_submitted.v1` / `srs.schedule_rebuilt.v1` / `mastery.updated.v1` | `CONTRACT-GAP-LRN-001`；可用的目标事件为 `learning.mastery.projected.v1`、`learning.review.scheduled.v1` | 先消除两套 SRS 写入口；不要把历史 `vocabulary.*` 和 B10 learning 事件并行记账。 |

事件 catalog 已把 154 个条目显式分为 12 个 `CANONICAL_D2` 和 142 个 `HISTORICAL_CANDIDATE`：M1-006 冻结的 7 个 workflow reliability 事件继续使用 `platform.workflow.v1`，M1-008 新晋升的 5 个 `content.version.*` 使用 `platform.content.v1`。这 12 个事件都必须具备已签收的 producer/data owner、consumer group、`aggregateId` 分区和生成式 AsyncAPI send/receive binding；其余业务事件在对应 M1-009…017 关闭 owner/consumer/schema 绑定前不进入 canonical AsyncAPI，也不得由 fragment 的 `x-kafka` 或默认值冒充正式事件。`EVENT-GAP-CONTENT-DUPLICATE` 与 `EVENT-GAP-BIND-CONT-001` 只关闭 D2 合同部分，其他 `EVENT-GAP-BIND-*` 仍为计划项；以上都不是 broker、Outbox 或 consumer 已运行的声明。

## 3. 进入实现或真实联调前的 Gate

任何 `INT-P1-*` 在标记为“可联调”前，至少需要以下可核验证据；缺一项仍为 `UNVERIFIED`：

1. OpenAPI/AsyncAPI/JSON Schema 的 operationId、eventName、payload、错误码、弃用窗口和客户端生成物可复现；对应 `CONTRACT-GAP`/`EVENT-GAP` 先关闭，不能用假 payload。
2. 事实 owner 的独立 schema/Flyway、写权限、Outbox、幂等表、消费者去重表和 Trace/Audit 字段就位；没有共享 ORM、跨服务 SQL 或 BFF 双写。
3. Gateway 路由与直连阻断、IAM JWKS/RS256、服务侧 PEP、401/403、tenant/owner/phase/content-rights/consent 负例通过。
4. 用真实浏览器经真实前端、Gateway、领域服务和 MySQL owner schema 驱动上表的最小写链路；对账 requestId/traceId、owner row、eventId、consumer result 和审计。CLI/API/SQL 只能辅助核对，不能替代浏览器证据。
5. 注入重复提交、超时、断连、消息重复/乱序、consumer 故障、DLQ、回放和 Saga 补偿；对权益、奖励、SRS、掌握度、审核和删除等不可重复事实验证无双写。

## 4. 当前优先收敛顺序

1. `CONTRACT-GAP-ONB-001/002`：先让“目标/定级 → 计划/首日”拥有可回放的 owner、事件和 Saga，否则首日主旅程无法真实闭环。
2. `INT-P1-006/007` 与 `CONTRACT-GAP-LRN-001`：冻结 attempt → mastery/SRS/D1/D7 的唯一写入口和事件链，避免两套 SRS 事实。
3. `CONTRACT-GAP-ADM-001`、`CONTRACT-GAP-COM-001`：在真实发布和商业准入前消除客户端角色输入与权益读取的安全歧义。
4. `CONTRACT-GAP-INF-001/002`、`CONTRACT-GAP-PRIVACY-EXPORT`、`CONTRACT-GAP-USR-DEL-001`：按 ADR-0014 已冻结的 owner 补齐客服、同步、导出、删除、补偿与审计契约后，才能对外承诺。
5. `INT-P1-017/018`：把 Outbox/DLQ/重放和 telemetry 隔离作为所有领域联调的共同平台 Gate，而不是每个页面各自补救。

本矩阵不增加 Phase 2 AI/RTC 或 Phase 3 未成年人/K12 能力；也不把 event catalog、目录、静态代码或本文档本身当成运行态完成证据。
