本矩阵把 Phase 1 的跨服务衔接登记为 `INT-P1-*`。它只定义**应被联调和验证的目标关系**：一个事实仍只由一个领域服务写入，跨域只使用已签收的 REST/internal API 或 Kafka + transactional Outbox 事实事件。矩阵中的“目标 consumer”不是“已有订阅/代码已运行”的声明；没有契约、topic、订阅、迁移和真实证据时，必须使用对应的 `CONTRACT-GAP`、`EVENT-GAP`、`IMPLEMENTATION-GAP`、`EVIDENCE-GAP` 或 `UNVERIFIED`。

## 1. Canonical 联调约束

### 1.1 每一条联调都必须满足

1. 外部请求统一经过 Gateway 的 `/api/v1`；Gateway 注入 `requestId`/`traceId`、预校验 JWT，但下游领域服务仍独立验签并执行服务侧 PEP。任何客户端角色、tenant、owner 或积分字段均不可信。
2. 写入由事实 owner 在自身 schema 内完成，并与 Outbox 同事务。Kafka 是至少一次投递；按照 `aggregateId` 分区，消费方按 `eventId`/业务去重键处理乱序、重试、DLQ 与回放。禁止跨服务 SQL、共享表写入、Kafka RPC 和两阶段提交。
3. 事件 envelope 至少保留 catalog 要求的 `eventId`、`eventName`、`traceId`、`requestId`、`schemaVersion`、`aggregateType`、`aggregateId`、`dedupeKey` 和脱敏 payload。Token、密码、支付回调原文、答案规则值、原始音频和未脱敏自由文本不得进入事件。
4. 同一个业务动作的客户端重试以 `Idempotency-Key` 和业务版本保护；M1-016 canonical 离线写入统一带 `clientEventId`、`clientSeq`、`baseVersion`、`contentVersionId`、`payloadHash`，旧 `baseCursor`/`entityVersion` 仅作历史适配输入。消费者不得依据 UI 数值重新计算奖励、权益或掌握度。
5. 当前本机验收治理仍以 B28/B36 的 `LOCAL-TEST-NO-PASS` 为准；因此本文件的测试证据栏写的是**最低必需证据**，不是通过结论。

### 1.2 事件命名收敛规则

`packages/contracts/events/v1/catalog.json` 是事件名、版本、payload schema、aggregate key 和兼容性规则的执行事实源。v2 域设计中存在不少“业务动作名”，其中有些不是 catalog 的 canonical 事件，另一些只是 UI 浏览行为。新的集成实现应按下表收敛，不得同时发布同义事件。

> **P1R-M1-014 当前源码覆盖规则**：INT-P1-008/009 行中的 `createB4*`、`finishB4*`、`consumeB12*`、`joinB4*`、`startB12*`、`renewB12*`、`leaveB4*`、`getB12*` 与 v1 事件名只保留为旧 B4/B12 联调追溯，不是 canonical 路由或事件；相关 `CONTRACT-GAP-GAM-001`、`EVENT-GAP-BIND-GAM-001`、`EVENT-GAP-BIND-SOC-001` 已在 M1-014 的 D2 静态治理中闭合。当前 operationId 以 merged OpenAPI 的 `M1014` 操作为准；当前 GAM/SOC 事件以 M1-014 policy、event catalog 与 AsyncAPI 的精确 v2 投影为准。该闭合不代表 topic、ACL、Outbox、consumer 或租约已通过 runtime 验证。

> **P1R-M1-015 当前源码覆盖规则**：`INT-P1-010` 的当前 canonical OpenAPI 是升级后的 B13 `M1015` 操作投影，当前事件是 M1-015 commerce v2 fragment 与 `config/p1r-commerce-contract.v1.json` 中精确列出的九个 v2 名称。B5 legacy 和 B13 v1 route/event 语义只作 historical input，不能双发、不能被客户端或旧 adapter 重新晋升；升级后的 B13 M1015 OpenAPI 本身不是 historical。B20 只保留 static Gate 输入，B21/B26 仍分别为 `NO-GO`/`pending`；本段只冻结 `D2_CONTRACT_READY / NOT_RUNTIME_VERIFIED`，不表示 provider、topic、ACL、Outbox、consumer、PEP 或支付链路已运行。

### 2.1 M1-009 媒体/录音 D2 边界

- 对 `INT-P1-005`，content-service 仍是内容版本、官方字幕文本、rights 和发布资格唯一 owner；media-service 只提供 asset/object/integrity/task/rendition/subtitle artifact metadata 与短时 grant。内容发布和到期排期重校验必须同时要求必需源媒体 `READY/CLEAN`、rights 有效、官方字幕或文本替代满足。源 rights 撤销后，源音频和官方字幕立即拒绝；不完整媒体不能借 content projection 分发。
- 对 `INT-P1-006`，media-service 只向 assessment-service 提供经过 PEP 的录音资源安全引用。assessment-service 独自拥有 shadowing session、规则化 attempt 和 self-rating，并且只有其可信结果才能进入 workflow → learning；录音保存、上传完成或 shadowing UI 完成不得直接写 `lrn_srs_state`、mastery 或奖励。
- 录音专用 consent purpose/version、已验证 subject、设备、content rights 和 phase 均由服务端 PEP 判定。用户主动点击后才申请麦克风；拒绝后保留静音练习。本地加密草稿与远端录音资产分态，远端录音回放默认 fail-closed；upload failure 可按 M1-007 幂等查询、重试、DLQ/replay/人工恢复语义处理。
- `media.started.v1`、`media.segment_completed.v1`、`recording.saved.v1`、`speaking.permission_requested.v1`、`shadowing.completed.v1` 在现有目录中仍为历史候选；M1-009 不自动将它们投影为 AsyncAPI/Kafka。仅当确有跨服务集成需要时，后续 canonical 事件必须补齐 producer、consumer、topic、aggregate partition、schemaVersion、dedupe 和 replay。
- 本节只冻结 `D2_CONTRACT_READY / NOT_RUNTIME_VERIFIED`。真实对象存储、扫描/转码/字幕 worker、DB/Flyway、Outbox/Kafka、Gateway/PEP、浏览器和真机恢复链路分别留给 M2/M3/M5/M8 Evidence。

### 2.2 M1-016 通知、同步与客服安全政策绑定

本节的字段、状态、owner 和禁止项以 [`config/p1r-notification-sync-support-contract.v1.json`](../../../../config/p1r-notification-sync-support-contract.v1.json) 为准，采用 strict/fail-closed：未知字段、未知枚举、缺少版本或隐式默认都拒绝。`B12` 是通知 v2 canonical family，`B11` 仅为 historical input；B5/B13 客服契约同样只允许 adapter 迁移，不能产生第二事实库。

通知的偏好使用 `category/channel/enabled/locale/consentVersion/dndWindow/frequencyPolicy/version/expectedVersion`，以 CAS 保护；模板到 source event 的 `templateKey/templateVersion/channel/locale/parameterAllowlist/deepLink/expiry/pin/dedupeKey` 必须逐项精确匹配。渠道为 `IN_APP/PUSH/EMAIL/SMS`，SMS 仅允许账号验证码、安全告警、手机号换绑和极重要账户支付，学习、营销和普通提醒不得走 SMS。消息、投递、读回执由 notification-service 拥有；workflow 只负责最多五次（含首次）重试、DLQ 和恢复。

通用同步不是新的领域 writer。owner-specific command 统一携带 `clientEventId/clientSeq/baseVersion/contentVersionId/payloadHash`，tenant/principal/device/owner 由服务端派生；同 hash 重复请求回放原结果，异 hash、乱序、gap、stale、future 或 content pin 不一致必须显式冲突。attempt、mastery、XP、entitlement 永远不能由客户端 merge，恢复任务由 workflow 持有且关闭前必须 owner reconciliation。

客服由 `admin-ops-service.support` 独占 ticket、message、assignment、SLA、resolution、retention。七态为 `OPEN/ASSIGNED/WAITING_USER/WAITING_INTERNAL/RESOLVED/CLOSED/REOPENED`，七类为 `ACCOUNT_SECURITY/CONTENT_CORRECTION/LEARNING_SYNC/MEDIA_DEVICE/ENTITLEMENT_ORDER/PRIVACY/OTHER`。内容只能用 `contentRefId + sha256 + redactionVersion + scanStatus + objectVersion + safePreviewRef`，附件只能用 media 授权引用且扫描为 `CLEAN`；法律保全为 `UNKNOWN` 时 fail closed。客户端不得设 tenant、subject、role、owner、assignment、SLA、priority 或 retention。

以上是 D2 契约绑定，不是运行声明。当前通知渠道、Kafka/Outbox、消费去重、重试/DLQ、客服路由/PEP、附件扫描、SLA 时钟、留存/法律保全和浏览器/设备 E2E 均仍需独立 Evidence；相关列的证据状态继续为 `UNVERIFIED`。

## 3. 进入实现或真实联调前的 Gate

任何 `INT-P1-*` 在标记为“可联调”前，至少需要以下可核验证据；缺一项仍为 `UNVERIFIED`：

1. OpenAPI/AsyncAPI/JSON Schema 的 operationId、eventName、payload、错误码、弃用窗口和客户端生成物可复现；对应 `CONTRACT-GAP`/`EVENT-GAP` 先关闭，不能用假 payload。
2. 事实 owner 的独立 schema/Flyway、写权限、Outbox、幂等表、消费者去重表和 Trace/Audit 字段就位；没有共享 ORM、跨服务 SQL 或 BFF 双写。
3. Gateway 路由与直连阻断、IAM JWKS/RS256、服务侧 PEP、401/403、tenant/owner/phase/content-rights/consent 负例通过。
