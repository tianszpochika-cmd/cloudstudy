## 1. 定位与权威关系

本目录补齐 `v2-980plus` 从“功能范围和域级设计”到“系统怎样实际运作”的中间层。它回答：

- 谁在什么页面发起业务；
- 页面执行什么功能、调用什么契约；
- 哪个服务和数据 owner 处理事实；
- 哪些事实通过 Outbox/Kafka 交给哪些消费者；
- 成功后进入哪里，失败后如何恢复或补偿；
- 用什么端到端证据证明业务闭环成立。

本目录属于 [`v2-980plus`](../README.md) 的现行组成部分，服从根 `AGENTS.md`、[文档治理](../../../00-vision/document-governance.md)、[v2 微服务架构](../../../02-architecture/v2-microservices-architecture.md) 和有效 ADR。它不新增 `V2-980-*` 数量，不把一个页面、接口或事件另算成产品功能，也不改变 Phase 1/2/3 边界。

如本目录与上级基线冲突，必须在同一变更中修正冲突和追溯关系，不能静默选择其中一份，也不能回退到旧 `phase-*` 或 B0–B6 文档取得现行定义。

## 3. 运行层标识

以下标识只用于运行设计追踪，不替代 `FEAT-*`、`PRD-ATOM-*`、`V2-980-*` 或 `ARCH-*`：

| 标识 | 含义 | 示例 |
|---|---|---|
| `ACT-P1-*` | Phase 1 参与者或系统角色 | `ACT-P1-LEARNER` |
| `JNY-P1-*` | 端到端业务旅程 | `JNY-P1-FIRST-DAY` |
| `PAGE-P1-*` | canonical 页面或工作区 | `PAGE-P1-TODAY` |
| `RULE-P1-*` | 确定性业务/学习规则 | `RULE-P1-SRS` |
| `INT-P1-*` | 跨页面、服务或事件联调链路 | `INT-P1-ASSESSMENT-PLAN` |
| `E2E-P1-*` | 可执行端到端验收场景 | `E2E-P1-FIRST-DAY` |

每个运行层标识最终仍须回指至少一个现有来源 ID 和相应 `ARCH-*`。运行层标识不得被用来绕过范围评审或凭空增加产品功能。

## 4. 缺口与完成状态

| 标记 | 含义 | 允许的下一步 | 禁止的表述 |
|---|---|---|---|
| `DESIGNED` | 业务流程和责任已定义 | 补契约或建立任务 | “已经实现” |
| `CONTRACT-GAP` | 缺少、重复或冲突的 OpenAPI/数据契约 | 先修正 `packages/contracts` | 让客户端临时猜字段 |
| `EVENT-GAP` | 事件名、schema、producer/consumer 或 topic 未闭合 | 先统一 AsyncAPI/catalog | 在代码中私造事件 |
| `IMPLEMENTATION-GAP` | 设计存在但页面/服务未实现或不可达 | 建实施任务并验证 | 以目录或静态文案报完成 |
| `EVIDENCE-GAP` | 功能可能存在但无真实运行证据 | 补 API/浏览器/数据/事件证据 | 引用旧截图或汇总声明 |
| `PHASE-GATED` | 不属于 Phase 1 默认路由 | 保持禁用，等待对应 Gate | 隐藏入口提前上线 |

一个项目项可以同时有多个 GAP。所有 GAP 必须有 owner、关闭条件和后续任务引用；没有真实 Evidence 时不得把 `DESIGNED` 升格为“完成”。

## 5. 所有旅程和页面的必填字段

```text
来源与阶段
→ 角色、前置条件和入口
→ 页面、主 CTA、输入与业务动作
→ Gateway operationId / internal contract
→ Service Owner / Data Owner / Security PEP
→ 事务事实 / Outbox 事件 / producer / consumer
→ 结果、下一页面和通知
→ 八态、幂等、离线、失败、补偿与人工恢复
→ E2E 场景、运行证据和回滚证据
```

任何字段暂时无法从现行事实源确定时必须填对应 GAP，而不是空白或推测为已实现。

## 6. 使用顺序

1. 产品、架构和业务 owner 先评审本目录的角色、旅程、页面和规则。
2. 对 `CONTRACT-GAP`、`EVENT-GAP` 做 contract-first 修正。
3. 依据 [08-验收与追溯规范](08-验收与追溯规范.md) 生成新的开发任务和依赖图。
4. 开发完成后按 `E2E-P1-*` 收集浏览器、API、数据库、事件、审计和恢复证据。
5. 只有运行证据和 Gate 通过后，任务状态才可从“设计/代码存在”升级为“验收通过”。
