# Phase 1 后台内容、运营、商业与客服业务流程

> 适用终端：`apps/admin-web`
> 原则：后台是受控命令和只读聚合入口，不是跨域数据库管理员
> 范围：内容生产/双审/发布、商业、客服、治理、隐私、审计和人工恢复

通知、同步与客服的安全/所有权冻结以 [`config/p1r-notification-sync-support-contract.v1.json`](../../../../config/p1r-notification-sync-support-contract.v1.json) 为唯一政策源。本文件补充运营流程，不把政策、静态校验或后台页面当作运行态证明；当前仍为 `D2_CONTRACT_READY / NOT_RUNTIME_VERIFIED`。

## 1. 后台运行边界

admin-web 通过 Gateway 使用后台权限调用 `admin-ops-service` 和各领域服务的受控命令/查询。它必须做到：

- 展示“谁、在何时、因为什么、对哪个版本做了什么”；
- 对内容、订单、学习、身份、奖励等事实只调用 owner 契约，不直接访问或写数据库；
- 作者、一审、二审、发布、财务、客服、隐私和审计职责分离；
- 高风险操作二次确认，关键操作双人批准或独立复核；
- 异步命令有 command/task ID、进度、失败原因和人工恢复入口；
- 导出默认脱敏并记录目的、范围、审批和下载审计。

后台页面隐藏按钮不能替代服务端 PEP。任何客户端传入的 actorId、reviewerId、role、tenant 或 owner 只可作为显示/兼容字段，不能成为授权事实。

## 2. 后台角色与职责分离

| 角色 | 主要权限 | 必须分离 | 高风险动作 |
|---|---|---|---|
| content-editor | 草稿、导入、媒体、校验、提交审核 | 不审核自己创建/修改的版本 | 批量导入、版权信息变更 |
| reviewer-l1 | 教学、格式、答案和来源一审 | 不得是作者；不能替代二审 | 一审放行/驳回 |
| reviewer-l2 | 版权、合规、媒体、最终内容二审 | 不得是作者；高风险内容不与一审同人 | 二审放行/驳回 |
| release-operator | 发布、定时、下线、回滚 | 不修改内容；不能跳过双审 | 发布、紧急下线、回滚 |
| finance | 订单、退款、对账和渠道异常 | 与客服权限分离 | 退款、补发/撤销权益建议 |
| support | 工单和受控恢复请求 | 不直接改订单、密码、分数或权益 | 账号/权益/内容纠错升级 |
| privacy | 导出、删除/匿名化编排和法律保留 | 与普通客服分离 | 全量导出、账号删除 |
| auditor | 只读审计和脱敏导出 | 不发业务命令 | 审计导出 |
| release/platform admin | Feature Gate、发布门禁、角色策略 | 双人批准；不得绕过领域 owner | Gate、策略、应急访问 |

Phase 1 tenant 由服务端派生为 `platform`。平台管理员不能通过空 tenant 或超级角色绕过 owner、版权、阶段、同意和隐私条件。

## 3. 内容供应链

### 3.1 内容身份与版本

`content-service` 为每个逻辑内容维护稳定 `contentId/contentCode`，每次修改产生新的不可变 `contentVersionId`。一个版本至少记录：

- content type、locale、目标等级、课程/单元/学习项关系；
- 题目、选项、答案规则和规则版本；
- 来源、作者、license/授权类型、授权凭证、地域、用途、开始/到期时间；
- 媒体资产 ID、hash、MIME、时长、字幕/文本替代和处理状态；
- 作者、审核决定、状态、content hash、创建/更新时间；
- 公开/学习者字段 allow-list；答案密钥和版权凭证不得进入学习端投影。

内容只能来自自有、开放许可或已经合法授权的来源。第三方品牌、教材、真题、词典释义、例句、音频、视频、图片和统计资料都必须绑定可核验证据；到期、超范围或证据缺失不得发布。

### 3.2 canonical 状态机

```text
内容版本（唯一持久状态）
DRAFT
  -- SUBMIT_REVIEW --> IN_REVIEW
  -- L1/L2 均通过 --> APPROVED
  -- PUBLISH 或到期执行成功 --> PUBLISHED
  -- 生命周期结束且不再作为可恢复版本 --> ARCHIVED

任一审核 -- REJECTED/CHANGES_REQUESTED --> 新 DRAFT version
PUBLISHED -- 新修订 --> 新 DRAFT version -- 重新校验和双审 --> 新 PUBLISHED version

发布指针与动作（不属于内容版本状态）
currentPublication = UNPUBLISHED 或 contentVersionId@contentEpoch
ROLLBACK = 将 currentPublication 切到一个已验证历史版本，并形成审计动作
```

canonical 内容版本状态只允许 `DRAFT/IN_REVIEW/APPROVED/PUBLISHED/ARCHIVED`；审核阶段标识只允许 `FIRST_REVIEW/FINAL_REVIEW`，每次审核决定使用 `APPROVED/REJECTED/CHANGES_REQUESTED` 并绑定独立 reviewVersion。审核进度是审核记录的投影，不再增加 `FIRST_PENDING/FIRST_APPROVED/FINAL_PENDING/FINAL_APPROVED` 这套平行状态机。`UNPUBLISHED` 是“当前无公开版本”的发布指针结果，`ROLLED_BACK` 是一次恢复动作和审计结果，都不得持久化为内容版本状态。为兼容旧 B9 读取模型而暂留的同名枚举只能标记为 deprecated/read-only alias，不能被新命令写入，也不能用来生成第二套状态机。

后台 `reviewRecords[]` 是按 `reviewStage` 键控、物理顺序无业务语义的服务端只读集合：空集合表示尚未审核；单条只能是 `FIRST_REVIEW`；双条必须各有且仅有一条 `FIRST_REVIEW` 与 `FINAL_REVIEW`。每条记录必须绑定不可变 `contentVersionId/contentHash` 并匹配 `versions[]` 中同一版本摘要；`FINAL_REVIEW` 只能在同版本、同 hash 的 `FIRST_REVIEW=APPROVED` 后产生。阶段重复、FINAL-only、跨版本/hash 拼接或客户端提交审核事实都必须拒绝；`APPROVED/PUBLISHED/ARCHIVED` 投影必须能证明两阶段均已批准。M1-008 只冻结并静态审计这套规则，真实跨记录校验由 content-service 实现和运行证据证明。

#### 3.2.1 ARCHIVED 内部退休边界

`ARCHIVED` 不是第 12 个 Admin 外部命令，也不是旧 `archiveContentVersion` 的直接结果。旧 archive 写入口只能迁移为 `UNPUBLISH`：清除当前发布指针，但保留版本作为可验证回滚候选。

只有 `content-service` 的内部退休处理器可以把 `PUBLISHED` 版本推进到 `ARCHIVED`，并且必须同时满足：当前发布指针已不引用目标版本；目标版本已不具备回滚资格；不存在可用中的 session/attempt pin，或版权、安全、法律紧急移除已把所有相关 pin 明确置为 `UNAVAILABLE`；调用方使用工作负载身份；expected stateVersion、退休原因、幂等键和审计关联完整。退休完成后版本为不可恢复终态，但历史作答、快照和审计引用仍按留存规则保存，不做物理级联删除。M1-008 只冻结该 D2 内部治理规则，不新增跨服务 canonical 事件；实现归 `P1R-M3-006`，真实 owner schema/事务证据归 `P1R-M2-004`。

### 3.3 创建、编辑和导入

1. editor 创建稳定内容身份和首个草稿，或从已发布版本创建新草稿；不原地修改已发布版本。
2. 保存草稿使用 expected stateVersion 和 Idempotency-Key；同键不同 payload 返回冲突。
3. 批量 CSV/JSON 导入先执行 `dryRun/validate`，生成逐行错误和 hash；只有无阻断错误且再次确认后才应用。
4. 重复 import batch hash 返回原报告，不重复创建内容。
5. 导入不能绕过来源、授权、答案规则、敏感词、locale、引用完整性和媒体校验。

canonical Admin 外部入口为：

- `listB9AdminContentStates` / `getB9AdminContentState`；
- `submitB9ContentCommand`，命令为 `CREATE_DRAFT/SAVE_DRAFT/VALIDATE_DRAFT/SUBMIT_REVIEW/REVIEW_FIRST/REVIEW_FINAL/PUBLISH/SCHEDULE_PUBLISH/CANCEL_SCHEDULED_PUBLISH/UNPUBLISH/ROLLBACK`。

现有 `createContentEntity/createContentVersion/submitContentVersion/...` 供应链接口可以作为迁移期内部/受控服务契约，但其中客户端 role header、actorId/reviewerId 不能继续作为外部授权事实。两套外部写入口必须收敛，见文末 `CONTRACT-GAP-ADMIN-CONTENT-BOUNDARY`。

### 3.4 自动校验

提交一审前至少检查：

| 校验域 | 阻断条件 |
|---|---|
| 结构 | 必填字段、ID 引用、locale、排序、题型 schema 或版本不合法 |
| 答案规则 | 无规则、无法解释、规则版本缺失、客户端可见答案泄漏 |
| 来源/版权 | 无凭证、过期、地域/平台/用途超范围、不可再分发 |
| 媒体 | hash/MIME/大小不符、处理失败或未 `READY/CLEAN`、字幕 artifact/文本替代缺失、rights 无效、敏感内容；录音资产不属于内容发布媒体，不得以录音完成代替内容媒体校验 |
| 学习闭环 | 无学习目标、无练习/反馈/完成条件或不可进入计划/课程 |
| 阶段 | 含 AI/K12/未成年人/未开放支付或 Phase 2/3 标记进入 Phase 1 |
| 安全 | 外部 URL、脚本、答案密钥、隐私或凭证泄漏 |

校验报告必须版本化、可下载并与 content hash 绑定。校验通过后修改任一受保护字段必须使旧报告失效。

### 3.5 媒体处理

1. content-editor 只能为待校验的 contentVersion 创建短时私有 upload intent；tenant、owner、actor、rights 和处理结论均由服务端派生，对象存储凭证不进入前端配置。
2. 上传完成后 media-service 以可信对象回执校验 hash、大小、MIME、对象完整性和归属；超时先按幂等键/任务 ID 查询，不能把客户端“完成”当作 `READY`。
3. media-service 维护 asset/object/integrity/task/rendition/subtitle artifact metadata；任务从 `QUEUED/PROCESSING` 进入 `READY/CLEAN`、`FAILED` 或 `QUARANTINED`。content-service 只保存媒体语义关联、官方字幕文本、版权/许可与发布资格。
4. 字幕 artifact 必须与 asset/contentVersion/语言/毫秒时间轴和完整性版本关联；字幕或音频不可用时，内容版本必须有文本或练习替代，不能以空白播放器替代。
5. 审核者使用短时预览 URL；学习端只获得已发布、rights 有效且通过设备/阶段/同意 PEP 的短时访问 grant。rights 撤销时源音频和官方字幕立即拒绝。
6. 个人录音另有专用 consent purpose：主动点击后才申请麦克风；`LOCAL_ENCRYPTED_DRAFT` 与远端 recording asset 分态，远端录音只归本人。上传失败可保留本地安全副本并按 M1-007 语义查询/重试。
7. retention 只引用 M1-017 的 policyRef/version；服务端检查 legal hold 并返回 delete/purge receipt，TTL 不是 retention。个人远端录音回放默认 fail-closed，删除/后续导出仍由隐私流程承接。
8. 原始录音、支付凭证、媒体源文件、永久对象 URL 和对象凭证不进入 Kafka、普通日志或 UI telemetry；B1/B3/B11 历史入口和历史媒体/录音事件不得自动晋升为新的 canonical 契约。

### 3.6 一审和二审

| 阶段 | 审核重点 | 允许决定 | 约束 |
|---|---|---|---|
| L1 | 教学准确性、语言、题目、答案、难度、格式、关联和可访问性 | APPROVED / CHANGES_REQUESTED / REJECTED | 作者不能自审；决定绑定版本/hash，不覆盖旧决定 |
| L2 | 版权、合规、敏感内容、媒体、Phase Gate、答案泄漏和发布风险 | APPROVED / CHANGES_REQUESTED / REJECTED | 与作者分离；高风险内容与 L1 分离；缺权利 fail closed |

驳回或要求修改后必须创建/更新草稿版本并重新校验；不能编辑已处于审核中的 hash 后沿用旧批准。审核备注结构化分类优先，自由文本按敏感数据规则保存和脱敏。

二审顺序由 `content-service` 的服务端事实强制执行：`REVIEW_FINAL` 只能在同一 `contentVersionId/contentHash` 的 `FIRST_REVIEW=APPROVED` 后发生；L1/L2 决定分别绑定独立 reviewVersion。发布资格还必须同时绑定 PASS 的 validation report、VALID 的 rights snapshot、全部必需源媒体 `READY/CLEAN`、官方字幕或文本替代满足、ALLOW 的 Phase/feature Gate 和匹配的 expectedStateVersion。editor、L1、L2、release-operator 四个主体在发布资格判断中必须互不相同；客户端不得提交审核阶段、审核者或这些资格结果作为事实。任一受保护内容 hash 变化都使旧校验和两级审核失效。

### 3.7 发布、投影和学习端可见

发布前 content owner 再检查：最新版本、L1/L2 通过、职责分离、rights 有效、全部必需源媒体 `READY/CLEAN`、官方字幕或文本替代、阶段/feature Gate、幂等键和 expected stateVersion；个人录音不能作为发布资格或内容资产替代。

成功发布时：

1. content schema 同事务写 `PUBLISHED` 和 Outbox；
2. canonical 事件使用 `content.version.published.v1`，以 content/version 为 aggregate；
3. 失效/重建 `cnt_public_projection`、learner catalog、official-site projection 和缓存 epoch；
4. 学习端只读 allow-list，不返回草稿、审核身份、版权凭证原文或答案规则；
5. 已开始 Session 保持原 `contentVersionId`，新 Session 使用当前发布版本；
6. admin 通过 commandId、projection watermark 和 auditId 查看进度。

公开与学习者投影必须同时携带 `contentEpoch` 和 `projectionVersion`；消费者只应用单调更新，旧 epoch、旧 projectionVersion 或未来排期版本只能返回明确的 stale/processing/not-yet-published 语义，不能覆盖当前安全版本。公开 allow-list 不含答案规则、草稿字段、审核者身份、授权凭证原文或内部任务信息。已开始 Session 固定 `contentVersionId`；只有版权、安全或法律要求触发的紧急下线才可把固定版本置为明确 unavailable，并提供原因与替代任务。

Phase 1 canonical 事件仅为 `content.version.submitted.v1`、`content.version.reviewed.v1`、`content.version.published.v1`、`content.version.unpublished.v1`、`content.version.rolled_back.v1`。它们统一使用平台 canonical 事件信封并通过 Outbox/Kafka D2 契约投影；旧 `cms.*` 只保留历史迁移语义，不得与 canonical 事件双发。`content.version.reviewed.v1` 必须携带 `contentVersionId/contentHash/stateVersion/commandId/auditId/reviewStage/reviewVersion/decision`，使审核决定能绑定不可变内容、owner 状态版本、命令和审计记录；按 `contentVersionId+contentHash+reviewStage+reviewVersion` 去重，不能发送 reviewerId、审核自由文本、版权原文或答案规则。`content.public_projection.invalidated.v1` 继续作为历史/owner 内部兼容名称；新设计以 content-service 内部失效、`contentEpoch/projectionVersion` 水位和可重建投影表达，不把缓存失效包装成跨服务 Kafka 事实。

#### 3.7.1 排期发布任务

排期发布是独立任务模型，不向内容版本状态机增加 `SCHEDULED`。`SCHEDULE_PUBLISH` 创建任务，`CANCEL_SCHEDULED_PUBLISH` 只取消尚未执行的任务；任务状态固定为 `SCHEDULED/CANCELLED/EXECUTED/INVALIDATED/RECOVERY_REQUIRED`，由 taskId 查询，不由客户端提交“执行成功”。

任务必须绑定 `contentVersionId/contentHash`、validation report、L1/L2 reviewVersion、rights snapshot/version、`scheduledAt`、IANA `displayTimeZone`、expectedStateVersion、Idempotency-Key、commandId 和 auditId。`scheduledAt` 使用带 offset 的 RFC 3339 时间，`displayTimeZone` 只负责解释与展示，不能改变实际 UTC 时刻。到期执行时必须重新校验版本/hash、双审职责分离、版权有效期、媒体状态、Phase/feature Gate 和并发版本；任何事实漂移都进入 `INVALIDATED` 或 `RECOVERY_REQUIRED`，不得沿用创建任务时的通过结果。真实调度、重试、补偿和人工恢复沿用 M1-007/M2-006 的统一恢复模型，本设计只冻结 D2 契约，不证明调度器已经运行。

### 3.8 纠错、下线和回滚

- 普通纠错：工单 → 新草稿 → 校验和双审 → 发布新版本。
- 严重准确性/版权/安全问题：release-operator 按审批执行 `UNPUBLISH`，阻止新访问并使下载/URL、源音频和官方字幕失效；随后修订。
- 回滚：选择一个仍具有效审核和版权证据的历史版本，说明原因、影响和目标；恢复动作产生新状态/审计，不删除中间历史。
- 下线/回滚后，进行中 attempt、SRS 和报告保留原 version 引用；页面提供安全解释和可学替代，不能让历史记录失联。

## 4. 运营 Dashboard、Feature Gate 和消息

Dashboard 只读取 analytics、各领域受控投影和数据水位，至少展示来源、asOf、延迟状态和筛选范围。DAU、留存、学习完成、内容使用、工单、风险和商业指标不能被 admin 页面缓存当成 owner 事实。

Feature Gate/运营配置变更流程：

```text
prepare → 显示影响/目标人群/阶段/回滚值 → 二次确认或双人审批
→ owner 写入版本化配置 → ops.flag.updated.v1 → 观测 → 回滚
```

客户端 feature flag 只能控制显示，服务端阶段/权限/版权/支付 Gate 仍必须执行。Phase 2 AI、Phase 3 K12、真实支付和未审核游戏不能因前端开关而开放。

运营消息和 Deep Link 必须选择 allow-list 的目标页面和资源，设置有效期、受众、频控和 fallback；URL 不含 Token、个人数据、分数、权益或可写权限。消息触达失败不改变源业务事实。

## 5. 商业、激活码、订单和退款

### 5.1 Phase 1 开放边界

- 免费版和激活码属于首发可用路径；
- SKU、订单、沙盒支付意图、回调验签、退款和对账可以开发/联调；
- 微信、支付宝、Apple IAP 生产开关默认关闭，未通过资质、平台审核、沙盒、退款、对账和隐私 Gate 不得开启；
- Phase 1 不提供自动续费。

### 5.2 激活码

```text
批次创建/导入（后台） → 状态/有效期/适用 SKU 校验
→ 学习者 redeemB13ActivationCode
→ 原子占用 → entitlement 激活 → 审计/通知
```

激活码只保存安全 hash，不能在普通后台列表批量显示明文。重复兑换返回原结果；已使用、撤销、过期、错误 SKU/tenant 明确区分。客服不能直接把码改为未使用。

### 5.3 订单和权益

```text
SKU/readiness → createB13CommerceOrder
→ prepareB13PaymentIntent（仅允许渠道）
→ 渠道签名回调 → commerce 验签/去重
→ payment verified → entitlement activated
→ 学习端 listB13MyEntitlements → content/service Gate
```

客户端支付成功页不授予权益。支付成功但权益未同步时进入对账/补偿，页面显示“权益同步中”，不能再次扣款。

### 5.4 退款、到期和对账

- `requestB13OrderRefund` 创建退款请求；finance 按订单、渠道、政策、历史和二次确认处理。
- 退款完成、拒绝、处理中和对账异常分别展示，不用人工直接改订单状态。
- 权益到期/退款后服务端撤销访问权，但保留合法学习历史、报告和个人数据权利。
- 渠道事件号/JWS、orderId 和 Idempotency-Key 去重；异常进入 `finance.reconciliation.discrepancy.v1` 和人工任务。
- 补发/撤销权益必须来源于已验证支付/退款/激活码事实，并有不可变流水；support 只能发起调查。

## 6. 客服工单

### 6.1 owner 冻结

Phase 1 的 `support_ticket`、ticket message、assignment、SLA、resolution 和 retention 由 `admin-ops-service.support` 的独立 support 子域拥有；`notification-service` 只拥有通知偏好、模板引用、消息、投递和读回执，`workflow-service` 只升级/恢复并拥有 retry/DLQ/recovery task，其他领域服务只提供受控查询和命令。该定义不允许 admin-ops 复制订单、学习、身份或内容事实，也不允许 workflow 或 notification 成为客服事实的第二写入者。

现有 learner `/api/v1/support/tickets*` 与 admin `/api/v1/admin/ops/tickets` 必须映射到同一 ticket owner、schema、状态机、版本和幂等域；B5/B13 只允许作为历史适配器。`CONTRACT-GAP-SUPPORT-ROUTING` 只在 M1-016 的精确 D2 投影、静态门禁和独立 Evidence 签收后关闭；这不等于真实路由迁移或双端 E2E 完成，后者仍必须保持 `UNVERIFIED`，同时禁止第二套工单库或双发事件。

### 6.2 流程

```text
学习者创建工单
→ 分类/严重级别/同意共享最小上下文
→ 自动路由到 support queue
→ 客服读取脱敏上下文
→ 回复、请求补充或发起领域恢复命令
→ 领域 owner 返回结果
→ 客服解释并解决
→ 学习者确认/超时关闭/规则期内重开
```

工单状态严格使用 `OPEN/ASSIGNED/WAITING_USER/WAITING_INTERNAL/RESOLVED/CLOSED/REOPENED`，不把旧实现的 `ACKNOWLEDGED/IN_PROGRESS/WAITING_CUSTOMER` 晋升为 v2 状态；允许的迁移必须带 `expectedVersion`，并形成独立 assignment/SLA history。关闭工单不能替代数据修复；每个恢复命令必须有 command/task/audit ID，且关闭前要收到 owner reconciliation receipt。

分类冻结为 `ACCOUNT_SECURITY/CONTENT_CORRECTION/LEARNING_SYNC/MEDIA_DEVICE/ENTITLEMENT_ORDER/PRIVACY/OTHER` 七类；B5/B13 的旧 category/ticketType 必须显式映射，未知值拒绝。自由文本、截图和附件不能以原文或裸 URL 进入 ticket/event/log，必须使用包含 `contentRefId + sha256 + redactionVersion + scanStatus + objectVersion + safePreviewRef` 的内容引用；附件只能使用 media owner 授权引用且 `scanStatus=CLEAN` 才可被客服读取。未知扫描结果或法律保全状态均 fail closed。

### 6.3 工单与消息的统一字段

学员和后台看到的是同一 `ticketId`、`stateVersion`、`messageVersion`、`assignmentVersion` 与 `lastAuditId`。Ticket 至少绑定 `categoryCode`、安全资源引用、脱敏描述引用、assignment、SLA、resolution 和 retention；Message 至少绑定 `clientMessageRef`、作者类型、内容引用、body hash、脱敏版本、附件引用和审计 ID。客户端不得设置 tenant、subject、role、owner、assignment、SLA、priority、state 或 retention；变更必须携带 `expectedVersion`，缺失或过期统一拒绝/返回冲突。

SLA 只保存 `policyRef/policyVersion/dueAt/status/history`，是配置化运营目标，不是对外承诺或运行完成声明；`WAITING_USER`、`WAITING_INTERNAL` 的暂停/恢复必须记录原因和审计。Retention 至少保存 `retentionPolicyRef/retentionPolicyVersion/retentionUntil/legalHold/ownerReceiptRef`；法律保全为 `UNKNOWN` 时禁止 purge/close 相关成功声明，TTL 不能替代 retention policy。

### 6.4 通知与同步的后台边界

客服回复、领域 owner 结果和状态变化可以触发规划中的 v2 `support.ticket.created.v2`/`support.ticket.resolved.v2` 通知，但消息内容只使用政策允许的模板参数和脱敏引用；客服不能直接写 notification delivery/read fact。通知失败最多重试五次（含首次），之后由 workflow 进入 DLQ/人工恢复，不回滚工单或领域事实。

离线同步由实体 owner 的受控 command 接收 `clientEventId/clientSeq/baseVersion/contentVersionId/payloadHash`；客服只可查看授权的冲突/恢复引用，不能替学习、attempt、mastery、XP 或 entitlement 合并事实。相同 hash 的重复请求回放原结果；异 hash、乱序、gap、stale、future 或内容版本不一致必须显式冲突，不能静默 last-write-wins。

## 7. 治理、风控和人工恢复

- 社交举报：social owner 保存举报事实，治理后台按权限读取、决定、申诉；Phase 1 不开放陌生人私聊或自由发帖。
- 风险：账号重放、设备异常、支付回调异常、激活码滥用、导出异常和内容版权过期形成结构化 case；风险决定有版本和 reason，不由页面本地判定。
- Recovery：`listB12RecoveryTasks/executeB12RecoveryCommand` 只触发 workflow 的重试、回放、补偿或关闭；不能让管理员直接修改 owner 表。
- DLQ：显示源 eventId、aggregate、consumer、错误、重试次数、schema 版本和影响；回放前先做兼容/幂等检查。
- 高风险应急访问有理由、时限、审批、最小权限和事后审计，不能成为常设超级账号。

## 8. 隐私导出、删除和账号注销

### 8.1 导出

学习者二次验证后调用 `createPrivacyExport`，选择范围并确认影响。`learner-service.privacy` 拥有 export request、状态和 receipt；`workflow-service` 只协调各领域 owner 生成数据片段，`audit-service` 留痕。`privacy` 角色只在异常/合规需要时介入。导出任务：

1. IAM 验证主体和 consent；
2. workflow 请求各 owner 生成最小、可理解的数据片段；
3. 合并、脱敏、加密，生成短时一次性下载；
4. 记录请求、目的、范围、生成、下载、过期和失败审计；
5. 到期删除导出副本。

### 8.2 注销和删除

```text
用户二次验证并查看影响
→ `iam-service` 创建并拥有 deletion request/cooling-off 与主体最终状态
→ 冷静期内可按规则撤销
→ workflow 向各 owner 发删除/匿名化命令
→ owner 返回 receipt
→ 对账全部 receipt 和法律保留
→ IAM 关闭会话并完成主体状态
→ 用户收到结果；部分失败进入人工恢复
```

法律要求保留的订单、退款、审计或安全记录必须最小化、匿名化/限制访问并记录依据。删除不能通过跨服务直写、删 Redis 或只停用登录来冒充完成。

当前 OpenAPI 只有隐私导出，缺少 deletion request、cancel/status、owner receipt 和 recovery 契约，标 `CONTRACT-GAP-PRIVACY-DELETION`。

## 9. 审计和导出

以下必须进入不可变审计：登录安全、角色/策略、内容审核/发布/下线/回滚、Feature Gate、支付/退款/权益、工单敏感查询、治理决定、隐私导出/删除、人工恢复和审计导出。

审计至少含：actor subject、服务端派生 tenant/role/permission、action、resource/version、before/after 摘要或 hash、reason、decisionId、requestId/traceId、command/event ID、结果和时间。密码、Token、完整支付凭证、答案密钥、原始音频和非必要自由文本禁止进入审计。

`listB13AdminAudit` 是只读入口；大规模导出必须另有审批、字段 allow-list、脱敏、异步任务、短时下载和下载审计。普通 CSV 按钮不能绕过导出治理。

## 10. 初始运营时效目标

以下是进入正式运营评审的初始目标，需由运营/合规确认后配置化；不是当前实现完成声明：

| 事项 | 初始目标 | 超时动作 |
|---|---|---|
| 普通内容 L1/L2 | 各 1 个工作日内首次处理 | 升级队列并通知 owner |
| 紧急版权/安全下线 | 批准后 15 分钟内阻止新分发 | 自动告警、应急 operator 和审计 |
| 发布到学习端投影 | p95 5 分钟内达到 CURRENT | 重建投影/缓存并生成 recovery task |
| S1 客服/安全事件 | 15 分钟确认、2 小时给出缓解 | 值班升级与事件审计 |
| 普通工单 | 1 个工作日内首次回复 | 自动升级队列 |
| 权益已付款未生效 | 15 分钟内自动对账，失败转人工 | 禁止重复扣款，通知用户处理中 |
| 隐私导出/删除 | 按适用法规和公开政策期限 | 超时告警、人工恢复和用户通知 |

实际对外承诺不得直接复制本表，必须经过法律、运营和容量评审。

## 11. 失败、补偿和回滚

| 场景 | 不回滚的 owner 事实 | 补偿/恢复 |
|---|---|---|
| 审核已通过，发布失败 | 审核决定和版本 | 保持 APPROVED，重试 publish command，不重复审核 |
| 发布成功，投影失败 | PUBLISHED 事实 | 重建 projection/cache；严重时显式回滚/下线 |
| 媒体处理失败 | 上传意图和资产元数据 | 重试 rendition 或替换资产；不得发布不完整版本 |
| 支付已验证，权益失败 | 订单和支付流水 | 对账补发 entitlement；客户端不重付 |
| 退款完成，投影延迟 | 退款流水 | 撤销/重建权益投影并通知 |
| 工单恢复命令失败 | 工单和领域原事实 | workflow 重试/DLQ/人工；不让客服直接改表 |
| 删除部分服务失败 | deletion request 和已成功 receipt | 对失败 owner 重试/人工恢复；不宣称完成 |

所有重试按 command/event ID 幂等；关闭 recovery task 前必须对账 owner 数据、投影和审计。
