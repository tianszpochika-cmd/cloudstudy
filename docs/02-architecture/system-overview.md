# 系统架构总览

## 设计原则

- 多端共享领域和契约，不共享所有 UI。
- 核心学习数据进入关系型数据库，媒体进入对象存储。
- AI 调用经过统一编排层，客户端不直接接触模型密钥。
- 实时语音与普通课程请求分离，避免互相影响。
- 异步任务可重试、可观测、可取消，并且具备幂等键。

## 逻辑拓扑

客户端层：学习 Web、微信小程序、移动端、官网、运营后台。

接入层：CDN、WAF、API 网关、鉴权、速率限制和 request id。

业务层：core-api 的账户、课程、学习、练习、复习、订阅、内容和运营模块。

智能层：ai-orchestrator 负责模型适配、提示词、工具调用、结构化输出、内容安全和成本策略。

实时层：realtime-voice 负责语音会话、转写、打断、会话事件和降级。

任务层：content-worker、notification-worker、analytics-worker 和 job-runner。

数据层：MySQL、Redis、对象存储、可选的检索索引和分析仓库。

## 运行策略

P0 以一个核心 API 部署单元承载大多数业务模块，专项 Worker 独立运行。这样既保留服务边界，又降低早期部署和排障成本。

## 关键请求流

### 今日学习

客户端 -> core-api -> 读取用户目标/课程进度 -> 生成今日任务 -> 返回任务链 -> 记录开始和完成事件。

### AI 练习反馈

客户端 -> core-api 保存原始答案 -> ai-orchestrator 读取课程上下文和评分规则 -> 返回结构化反馈 -> core-api 写入反馈和复习项 -> analytics-worker 消费事件。

### 语音角色扮演

客户端建立实时会话 -> realtime-voice 管理音频和转写事件 -> ai-orchestrator 处理角色和安全策略 -> 会话结束后由 worker 生成摘要、反馈和复习项。
