# ADR-0009：v2-980plus 作为下一轮设计与任务重基线

- **状态**：accepted
- **日期**：2026-08-22
- **范围**：需求追溯、设计包、架构能力、Backlog 和验收治理
- **取代/影响**：旧 B0–B6 任务台账保留历史追溯，但不再作为 v2 新任务的唯一拆分依据

## 背景

`docs/06-design/v2-980plus/` 已形成第二版 980 个设计单元、四个前端项目边界、三阶段 Gate、页面八态、契约/数据/事件和验收追溯。旧的 14 章、140 个 `DEV-*` 任务是在 v1 技术基线（Java 17 + Spring Boot 3 模块化单体）上组织的，不能直接承载新的 Gateway、IAM/RBAC、服务数据所有权和微服务运行治理要求。

如果继续把旧任务当作新版本的开发入口，会产生三个问题：

1. 把业务 Feature 与平台能力混在同一个编号体系中；
2. 把旧 `core-api` 的代码层推进误认为 Gateway、RBAC 和微服务已经完成；
3. 在已属于 v2 范围、但尚未细化到独立名称和验收的 `V2-EXT-*` 单元上提前创建代码任务。

## 决策

1. `v2-980plus/` 是下一轮开发唯一的全量业务设计与需求落地基线；`feature-matrix.md` 仅保留 `FEAT-*` 编号、阶段统计和来源追溯，不能以 v1 文案覆盖 v2。
2. 平台和架构能力使用 `ARCH-*` 编号，登记在 [v2 平台能力矩阵](../02-architecture/v2-platform-capability-matrix.md)；它们不增加 980 个业务设计单元的数量。
3. 只有经过 v2 设计、架构和合规签收的 `FEAT-*`、`PRD-ATOM-*`、`V2-980-*` 才能转成新的 v2 任务；`V2-EXT-*` 属于 v2 范围，但在细化签收前不得进入 WBS、契约或默认路由，也不得回退到 v1 寻找定义。
4. 旧 B0–B6、`DEV-*` 台账和历史状态报表改为“legacy/historical baseline”。不删除历史记录，不擅自重判已有代码状态；新的任务台账必须重新建立并标注 `Source Ref`、`Arch Ref`、服务 owner、契约、数据 owner 和证据包。
5. `services/core-api` 是迁移中的 v1 兼容单体。它可以作为 Strangler 迁移的反腐层和回滚边界，但不能继续被描述为 v2 的最终后端架构。

## 结果与迁移

- 新任务先建设 Platform 0（Gateway、IAM/RBAC、契约、观测、服务模板和数据/事件边界），再按领域抽取服务。
- 旧任务的历史完成情况仍可用于审计，但“已完成”只代表旧任务自身证据，不代表对应的 v2 架构能力已完成。
- 需求、设计、架构、验收和 Roadmap 必须同时引用本 ADR 与 ADR-0010；冲突登记保留在原文档中，不能通过静默改名解决。
