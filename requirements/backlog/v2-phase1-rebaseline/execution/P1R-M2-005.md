## E2（本轮交付）：Outbox 形状标准化 + ADR-0015

### 侦察：形状分歧是系统性的

`[实测]` 10 张 `*_outbox_event` 表**形状各异**，且**全部缺认领与错误字段**：

| 缺口 | 涉及表 |
|---|---|
| `locked_by` / `locked_until` / `published_at` / `last_error_code` / `last_error_message` / `updated_at` | **全部 10 张** |
| `request_id` / `trace_id` / `occurred_at` | learner、commerce、media、gamification、assessment、admin-ops、learning |
| `event_name` | commerce、learner（用 `event_type`）、learning_runtime（用 `event_type`） |
| `dedupe_key` | commerce |
| 整个状态机（`status`/`attempt_count`/`available_at`） | commerce、learner（用 `published_at`）、analytics |

同一概念三种命名：`event_name` vs `event_type`、`status` vs `state`、`payload_json` vs `payload`。

**并确认**：`analytics_event_journal` 是**消费者去重日志**（契约 `consumer-service-owned-idempotency-record`），**不是 outbox**，因此不套用 outbox 形状 —— 该判定已写入 ADR。

### 决策：ADR-0015

`docs/10-decisions/0015-event-transport-and-outbox-shape.md`。四条决策：

1. **标准 outbox 形状唯一**：以 `content_outbox_event` 的完整形状为基线，叠加项目自身 `yuxuexing.outbox_events` 已有的认领/错误字段；`(status, available_at)` 建索引供 `FOR UPDATE SKIP LOCKED` 认领。
2. **传输实现留在服务内，共享的是契约与形状而非运行时库**：发布器必须读**本服务** outbox、在**本服务**事务内落去重记录；做成共享运行时库会引入跨服务耦合，而 AGENTS.md §3.2 要求每服务自有 schema/凭据/写权限。共享语义，不共享进程内代码。
3. **去重记录归消费方服务**，唯一键 `(consumer_group, event_id)`，与业务效果**同事务**落库。
4. **DLQ 与 replay 由运维/平台负责**（契约 `adminClientInApplication: false`、`dlq.operatorOnly: true`）：topic 外部供给；服务只负责把耗尽重试的事件按契约字段投递到 DLQ，**不得**改写真领域事实。

**明确不做破坏性重命名**：已有的 `event_type`/`state`/`payload` 保留原列与值，发布器通过**显式列映射**读取；新代码一律写标准列。

### 交付：10 份非破坏性迁移

每份迁移 = 补列 → 从旧列**回填** → 收紧为 `NOT NULL` → 建认领索引。

**应用结果** `[实测]`：

| 项 | 结果 |
|---|---|
| `reconcile --apply` | 9 个 owner `applied-N-pending`（learning 两张表 → 2 份迁移）；social/analytics/audit `up-to-date`；**12/12 授权仍 DML-only** |
| 复查缺口 | **10 张 outbox 表全部「缺 0」**（列数 19–26） |
| `analytics_event_journal` | 仍报缺 14 —— **符合设计**（去重日志非 outbox） |

**E2 未覆盖**：Kafka 依赖与 BOM、发布器实现、消费者去重实现、DLQ 投递与 replay，以及六类运行时证据。

## E3（本轮交付）：content-service 的 Outbox 发布器

### 侦察

`[实测]` content-service 的**写入侧完整**（`ContentOutboxPort` + `JdbcContentOutbox`/`InMemoryContentOutbox`/`FailClosedContentOutbox` 三适配器、`ContentOutboxEvent` 域记录含完整校验），且 `JdbcContentOutbox` 已写标准列；**但没有任何组件消费 outbox** —— 每个 append 的事件**永远停留在 PENDING**。这正是契约 `outbox.publisher` 段所要求而缺失的部分。

### 交付

| 文件 | 职责 |
|---|---|
| `port/ContentOutboxRelayPort.java` | 发布侧端口：`claim` / `markPublished` / `markFailed` / `reclaimExpiredLeases` |
| `adapter/jdbc/JdbcContentOutboxRelay.java` | `SELECT … FOR UPDATE SKIP LOCKED` 认领 → 短事务内转 `PUBLISHING` 并盖租约；**发布前不持锁** |
| `integration/ContentOutboxKafkaRelay.java` | `@Scheduled` 轮询：先回收过期租约 → 认领 → 发布 → 依确认结果落地状态 |
| `config/ContentEventRelayProperties.java` | 契约 publisher 块的参数（topic / 批 100 / 租约 30s / 5 次 / 1s→60s） |
| `config/ContentEventRelayConfiguration.java` | 装配；**默认关闭**（`content.events.relay.enabled=false`），未配置 broker 不得悄悄改变投递语义 |

语义严格对齐契约：
- **broker 确认后才标记已发布**（`publishConfirmation: broker-ack-before-mark-published`）；
- 可重试失败 → 有界指数退避 + 抖动重新排期；**不可重试失败跳过预算直接入 DLQ**；预算耗尽 → `DLQ` 并记录错误码与消息，**不丢弃**；
- 每次轮询先 `reclaimExpiredLeases`，**崩溃的 relay 不会让行滞留**；
- **任何地方都不声称 exactly-once**：ack 与 `PUBLISHED` 之间崩溃会产生合法重复，正是消费侧 `(consumerGroup, eventId)` 去重要吸收的；
- producer 开启幂等（broker 内部重试不产生重复），投递声明仍是 at-least-once。

### 验证

`[实测]` `mvn -o test`：新增 **7 项确定性测试全通过**（用手写 fake，符合该服务既有测试风格），断言：确认先于标记、信封头与 aggregateId 分区键、首答与倍增退避窗口、耗尽与不可重试两条 DLQ 路径、退避上限、租约回收；content-service **全量套件无失败**。

> 其中一项测试**初次失败在我写错的夹具上而非代码**：`attemptCount` 是认领**之前**读到的值，因此已是 1 的事件处于第 2 次尝试，等待 2050ms 是**正确的**。已修正夹具并补一条"退避逐次倍增"的断言。

### 过程中修正的两处测量错误（都是我的，不是系统的）

1. **`kafka-get-offsets.sh` 的和不是消息数**：它是**日志末端偏移**（单调计数器），包含已被 retention 删除的记录。修正为按分区取 `latest − earliest` 得到**保留消息数**（67 − 20 = 47），才与 outbox 的 47 条可比。证据文件同时记录两者并注明差异原因。
2. **先前的「topic 基线 0 条」不准确**：本次运行期间有约 20 条更早的消息被 retention 删除，说明采集基线时那次 `--from-beginning` 读取并不可靠（冷启动超时）。最终判定不依赖该基线，而依赖「47 个不同 eventId、重复 0」这一直接观察。

### 运行时暴露并修复的 4 个缺陷（**全部是我自己的**）

1. **`ExponentialBackOff` 默认 `maxElapsedTime` 无限** → 安全网错误处理器对一条畸形记录**永远重试**，把它停在分区头部，**堵塞该分区后续所有记录**（DLQ 为空、位点永不提交）。已改为按 `maxAttempts` 推导预算，超时即入 DLQ。
2. 信封读不出的记录原先在监听器的 try/catch **之外**抛出 → 交给上述处理器无限重试。现在**在监听器内直接投 DLQ 并 ack**。
3. 探针生产者需要 **`parse.key=true` 与 `parse.headers=true` 同时给**，否则 key 为 null 且 key 文本混入 value。
4. **PowerShell 向原生命令管道传输会加 UTF-8 BOM**，把第一个头部名污染成 `U+FEFFeventId` —— 这才是「缺 eventId」与无限重试的**真正起点**。探针已改为写入无 BOM 文件。

**装配缺陷**：`@KafkaListener` 默认查找名为 `kafkaListenerContainerFactory` 的 bean，与本服务命名空间化的工厂不符 → 启动即 `NoSuchBeanDefinitionException`；已显式指定 `containerFactory`。

## E7（本轮交付）：可复现的事件运行时 harness

`scripts/runtime/p1r-m2-005-event-runtime.mjs`（`pnpm p1r:m2-005:events`），三个阶段各自**只写自己的探针行并在结束时清理**：

| 阶段 | 断言 |
|---|---|
| `--dedupe` | 同一事件投递 3 次 → **1 条回执 + 1 次效果** |
| `--ordering` | 同一聚合的 3 个事件 → **同一分区**且**按发布顺序消费** |
| `--dlq` | 信封可解码但不完整 → **进入 DLQ** |

证据归档 `evidence/p1r/m2/P1R-M2-005/event-runtime-harness-2026-09-12.json`。`[实测]` 三阶段**全部 PASS**：

```
dedupe   : deliveries=3 receiptRows=1 appliedCount=1
ordering : consumedOrder=[0,1,2]  同一分区、按发布顺序
dlq      : dlqLogEndOffset 17 -> 18
```

### 关于「乱序」的诚实界定（重要）

`[读取]` 契约 `eventEnvelope.partitionKey = aggregateId`，且 `consumerReliability` 中**没有任何陈旧版本/排序规则**。契约的排序模型是：**同一聚合的事件由分区键保证落同一分区、分区内有序**，重复由 `(consumerGroup, eventId)` 去重吸收。

因此本 harness 证明的是**契约真正承诺的东西**（同一聚合同一分区 + 按发布顺序消费），**没有发明契约未要求的「陈旧版本拒绝」语义**。

### 本次运行时暴露并修复的 2 个 harness 缺陷

1. **`cmd /c` 的嵌套引号被 Node 重新转义** → 生产者调用整体失败（`producer-accepted: FAIL`）。改为用 `spawnSync` **直接写子进程 stdin**（Node 原样写入、不加 BOM），同时省掉了临时文件与 shell 重定向。
2. DLQ 探针原先用**空头部段**，被 console producer 自身拒绝。改为**有头部但缺必需字段**的记录（可解码但不完整），这才真正触发监听器内的「信封不可读 → 直接 DLQ」路径。

**E7 仍未覆盖**：broker 宕机/恢复的**脚本化**（E4 为手工验证）；DLQ 事件的**发布侧回放**入口。

## E8（本轮交付）：DLQ 运维回放入口 + 脚本化故障阶段

### 交付

| 对象 | 作用 |
|---|---|
| `scripts/runtime/replay-dlq.mjs`（`pnpm p1r:m2-005:replay`） | 运维回放入口：**不加入消费组**读取死信（不干扰服务在 DLQ 上的位点）、只把**信封**重新发布回原始 topic、把 DLQ 的失败字段留在原处；`--plan` 只读、`--apply` 执行，支持 `--event-id` / `--limit` |
| `ContentInboundEventConsumer` | 每条死信记录 **`originalTopic`** |
| harness `--fault-db` | 在**与 M2-001 同一套 opt-in 纪律**下暂停 MySQL（精确容器名 + 精确 opt-in 串），使一个**可读**事件瞬时失败、耗尽重试预算进入 DLQ 且**不生效**，随后恢复 MySQL |
| harness `--replay` | 回放死信 → 断言效果**恰好生效 1 次** → **再次回放** → 断言回执吸收重复 |

### 完整 5 阶段运行时证据 `[实测]`（全部 PASS）

```
dedupe   PASS  deliveries=3   receiptRows=1  appliedCount=1
ordering PASS  consumedOrder=[0,1,2]（同一分区、按发布顺序）
dlq      PASS  dlqLogEndOffset 19 -> 20（不可读信封直达 DLQ）
fault-db PASS  MySQL 暂停 -> 可读事件入 DLQ、receiptRows=0（未生效）-> MySQL 恢复
replay   PASS  afterFirstReplay={receipts:1,applied:1}
               afterSecondReplay={receipts:1,applied:1}   ← 二次回放无法二次生效
```

**契约要求的六类证据现已全部具备且可脚本化复现**：重复、乱序、宕机、重启、DLQ、回放不重复写。

### 两个设计判断

1. **`originalTopic` 是契约之外的附加运维元数据**：契约的 `dlq.requiredFailureFields` 未包含它，但**没有它，回放只能猜原始 topic，而猜错就是把事件写进错误的领域**。框架自带的 recoverer 以 `kafka_dlt-original-topic` 记录同一事实；本监听器以稳定名记录。已在代码注释中说明理由。
2. **回放安全可重复**：消费侧回执以 `(consumerGroup, eventId)` 为主键，因此回放天然幂等 —— 这正是它敢被重复执行的原因。

### 本次暴露并修复的缺陷

**console consumer 不解析 `\uXXXX` 转义**：回放工具原用 `key.separator='\u0001'` / `headers.delimiter='\u0002'`，实际未切分，导致 `originalTopic` 把头部的后续内容全部吞入（解析出 `platform.iam.v1\u0001p1r-...`）。已改用其支持的默认制表符分隔 —— 头部段以逗号分隔、载荷为 JSON，**制表符不会出现在字段内**，切分无歧义。

### E8 未覆盖（诚实标注）

- **broker 宕机/恢复的脚本化**仍缺：`--fault-db` 暂停的是 MySQL；Kafka 的停止/重启仍只有 E4 的手工验证。
- 其他消费组的去重表尚未建立（当前仅 content-service 这一条垂直切片）。
