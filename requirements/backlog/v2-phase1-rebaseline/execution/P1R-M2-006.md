## 2. ⚠️ 受阻项：Gateway → canonical ingest **缺服务间认证机制**

**已完成的**：`HttpSecurityAuditSink` ✓ —— 网关此前只有两个 sink（内存有界缓冲 ✗、stdout 投影 ✗），其配置的 javadoc **自述**"neither bean is a durable audit-service adapter" ✗。新 sink 把脱敏记录投递到 canonical ingest ✓，**在请求线程之外** ✓、**失败不使请求失败** ✓、**失败与关闭期丢弃均计数** ✓（3 项测试 ✓，含真实投递失败 ✓）。

**受阻的**：网关**拿不到可用的凭据** ✗。三项实测事实：

1. `[读取]` `iam-service` **没有** service-token / client-credentials 端点 ✗
2. `[读取]` `audit-service` 的 `/internal/v1/audit/**` 要求**已认证 JWT** ✓ 且校验 **issuer + audience** ✓
3. `[读取]` `AGENTS.md` §2.2：**"`iam-service` 是唯一 Token 签发方，领域服务、Gateway 和客户端均不得自行签发"** ✗

⇒ 网关**不能自签** ✗、**无处可取** ✗ ⇒ **服务间认证机制缺失** ✓

**为何不由我实现** ✓：AGENTS.md §3.4 规定"**引入新基础设施或改变服务边界必须新增 ADR**" ✓，而服务间认证正属此列 ✓。按目标"无法解决就跳过" ✓ 与 §7"需要变更架构边界或新增 ADR → 停下来报告人类" ✓，**记录而不擅自发明** ✓。

**建议的方案（供裁决，未实施）**：
- **A**：IAM 增加**服务令牌**端点 ✓（如 `POST /internal/v1/auth/service-token`，以服务身份 + 客户端凭据换取短时 JWT ✓，claim 含 `svc:api-gateway` + `audit.ingest` ✓）—— 保持"IAM 唯一签发方" ✓
- **B**：网关与 audit 之间用 **mTLS + 服务身份头** ✓ —— 不经 JWT ✓，但需证书分发 ✓
- **C**：由 M2-007（配置/密钥）先建立**服务间凭据**基础设施 ✓，M2-006 接入 ✓

**推荐 A** ✓：符合"仅 IAM 签发" ✓、改动最小 ✓、且 `audit.ingest` 权限模型已存在 ✓。
