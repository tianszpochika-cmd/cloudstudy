# M3–M8 资产预检报告

> 日期：2026-09-10
> 范围：`M3`–`M8` 中资产策略含 `REUSE-VERIFY` 的 **22 项任务**
> 方式：4 个只读子 agent 并行核查 + 主评审抽样复核
> 结论产出：已回填至 [02-编号任务台账](../02-编号任务台账.md) 的「资产验证」列

## 一、背景

`B0–B36` 任务线的最终结论是 `LOCAL-TEST-NO-PASS`，其产物被登记为「可复用资产候选」，但**从未在 v2 架构下完成整体验收**。而 `P1R` 中 86/108（80%）任务涉及旧资产，其中 22 项 `REUSE-VERIFY` 集中在尚未启动的 `M3`–`M8`。

为落实 [01-里程碑与依赖图 §3.1 资产预检门](../01-里程碑与依赖图.md)，本次提前执行预检，避免开工后才发现资产不可用。

## 二、结论摘要

| 判定 | 数量 | 含义 |
|---|---:|---|
| `已验-可用` | **12** | 可直接复用 |
| `已验-需修` | **10** | 可复用，但需 `REPAIR` |
| `已验-不可用` | **0** | — |

**三条核心结论：**

1. **没有一项需要整体 `REWRITE`。** 22 项的域模型与 UI 骨架均可复用，缺口集中在**集成层与完整度**，不在架构。
2. **架构基线是对齐的。** 核查确认 `services/` 下全部服务均为 **Java 25 + Spring Boot 4.1.1**，无 Java 17 单体或旧 API 残留；代码即 B0–B36 交付物（控制器仍留 B3/B9/B25 命名痕迹）。
3. **共性风险是测试覆盖极薄。** 多个模块仅 1 个 smoke 测试（`learning` / `assessment` / `content` / `media` 各 1；`admin-ops` 0）。

## 四、风险清单（按严重度）

### R1 · 架构合规风险（最高）

**可信事件未接 Kafka/Outbox** —— `gamification-service` 与 `social-service` 的可信完成事件走**受信 HTTP 直接推送**，未接入 v2 事件骨干。

- 影响任务：`P1R-M7-001`、`P1R-M7-004`
- 为什么严重：v2 架构规则明确「Kafka + transactional Outbox 是 v2 事件唯一事实源」。这是**架构合规问题，不是可选优化**。
- 建议动作：接入 `M2-005` 建立的 Outbox 与事件骨干，改造为「写本地事实 → Outbox 发布 → 消费者幂等处理」。

### R2 · 阻塞风险

**`learning-service` 无 v2 HTTP 控制器** —— web 层仅有 B25/B3 的 JDBC 残留控制器，缺 v2 的计划/首页/今日端点。

- 影响任务：`P1R-M4-008`
- 连带影响：前端 `HomePage`(36 行) / `TodayPage`(25 行) 为**桩页**，八态未实现。
- 建议动作：`REPAIR` —— 按 v2 契约新建 HTTP 适配层，并同步补前端八态。

### R3 · 误引风险

**`core-api` 旧基线残留** —— 存在 `B2AssessmentEngine`、`InMemoryIdentityRepository` 等旧实现。

- 影响范围：`M5` 全域（学习/测评/SRS）
- 为什么严重：`core-api` 是**迁移中的 v1 兼容单体**，其实现不得进入 v2 正式路径。误引会导致信任边界失效。
- 建议动作：在 `M5` 相关任务开工前，明确列出「禁止引用的旧路径清单」。

### R4–R9 · 功能缺口（需在对应任务内 `REPAIR`/`NEW`）

| 编号 | 缺口 | 任务 | 类型 |
|---|---|---|---|
| R4 | 内容**批量导入**无实现 | `P1R-M3-002` | `NEW` |
| R5 | 官网缺 **4 个合规页**（privacy/terms/minors/status） | `P1R-M3-008` | `NEW`（涉合规，工期易低估） |
| R6 | 支付回调**缺专门安全测试** | `P1R-M7-007` | `REPAIR`（安全路径必须补） |
| R7 | `admin` 缺**退款操作工作台** | `P1R-M7-009` | `NEW` |
| R8 | 音频**波形未真实现**（仅 CSS 装饰） | `P1R-M5-004` | `REPAIR` |
| R9 | 通知缺**订阅表与模版实体** | `P1R-M6-001` | `NEW`（数据模型） |

另有：`P1R-M5-001` 的「替代内容」无服务端类；`P1R-M6-004` 前端设置页偏薄。

### R10 · 共性风险

**测试覆盖普遍极薄** —— `learning` / `assessment` / `content` / `media` 各仅 1 个 smoke 测试，`admin-ops` 为 0。

- 影响：所有 `已验-需修` 项在修复后，都必须补齐关键路径测试，否则无法通过 Evidence Gate。
- 建议动作：把「补测试」写进每个 `REPAIR` 任务的退出条件，而非留到最后统一补。

## 五、核实与修正记录

本次预检对子 agent 的结论做了**抽样复核**，发现并修正了一处**结论性错误**：

> 某子 agent 报告称「**IAM HTTP 层严重缺失**：注册/登录/重置与设备/会话管理均无 HTTP 控制器」，并列为「最大阻塞点」。

**经核实为误判。** `services/iam-service/src/main/java/com/englishflow/iam/web/IamProviderBoundaryController.java`（1203 行）中，**文件名有误导性——内部类名实际是 `IamAuthenticationController`**，注释写明其为「平台自有账号密码与 JWT 认证中心的 HTTP 适配器」。该文件实现**全部 15 个端点**：

```
/api/v1/auth/register              (L117)   /api/v1/iam/principal/me      (L282)
/api/v1/auth/login                 (L133)   /api/v1/iam/permissions       (L289)
/api/v1/auth/token/refresh         (L149)   /api/v1/iam/devices           (L299)
/api/v1/auth/logout                (L192)   /api/v1/iam/devices/{id}/kickout (L313)
/api/v1/auth/sessions/{id}/revoke  (L220)   /api/v1/iam/adult-gate        (L339)
/api/v1/auth/jwks                  (L242)   /api/v1/iam/consents          (L369,386)
/api/v1/auth/password-reset/request(L248)
/api/v1/auth/password-reset/confirm(L267)
```

`IamSecurityConfiguration:41-43` 亦声明这些端点为首批 `permitAll`。

**因此 `P1R-M4-001` 修正为 `已验-可用`；`P1R-M6-004` 的「端点缺失」理由不成立，其 `已验-需修` 仅因前端页面偏薄。**

**教训**：① 子 agent 可能仅凭文件名判断而未打开文件正文；②「文件名与内部类名不一致」是真实存在的陷阱；③ **子 agent 的结论必须抽样核实后才能采信**。

## 六、对后续开发的影响

1. **`M3` 可以开工**：4 项中 2 项可用、2 项需修，缺口明确且可控（批量导入、4 个合规页）。
2. **`M7` 开工前必须先处理 R1**：事件骨干集成是架构合规前置，否则做完也要返工。
3. **`M4-008` 是 `M4` 的硬骨头**：learning 的 HTTP 层要从头建，且前端八态同步补。
4. **`M5` 必须先出「禁止引用清单」**：防 `core-api` 旧实现误入正式路径。
5. **测试是横切要求**：建议把「补测试」并入每个 `REPAIR` 的退出条件。
