### 首次执行即发现并修复一个真实解码缺陷

首次 `node services/api-gateway/src/test/runtime/p1r-m2-001-runtime.mjs --run` 返回 `BLOCKED / HTTP_STATUS`，失败点为 `protected-iam-upstream`。用保留子进程日志的诊断批次手工复现后确认：

- IAM 注册返回 **201**，签发的 access JWT 完全合法（`alg=RS256`、`typ=JWT`、`iss=http://127.0.0.1:18087`、`aud=yuxuexing-api`、`tenant_id=platform`，`exp/iat/nbf/jti/token_type/scope` 齐备）。
- 用该 token 访问 `/api/v1/iam/principal/me` 一律 **401**；Gateway 审计行为 `routeId=iam-domain, decision=DENY, reasonCode=unauthorized, latencyBucket=LT_50_MS`，即**网关在本地即拒绝，令牌从未转发到 IAM**。
- 网关 debug 日志给出真实原因：`HTTP GET http://127.0.0.1:18087/api/v1/auth/jwks` 请求成功，但 `com.nimbusds.jose.jwk.JWKSet.parse` 解析失败 → `JWT decoding failed` → 401。

根因：IAM 按冻结契约把 `/api/v1/auth/jwks` 发布为 `ApiSuccessEnvelope`（`{"data":{"keys":[...]},"meta":{...}}`），而 Gateway 使用 `NimbusReactiveJwtDecoder.withJwkSetUri(...)`，该解码器把**整个文档**交给 `JWKSet.parse`，只接受顶层即 `{"keys":[...]}` 的裸 RFC 7517 JWK Set。该缺陷此前不可见，是因为既没有测试覆盖「用项目信封格式的 JWKS 成功验签」，本机也从未真实跨进程执行过本批次。

修复（提 `51a86c8`，遵循契约先行：契约是唯一事实源且 IAM 实现符合契约，故修消费侧）：

- 新增 `services/api-gateway/src/main/java/com/englishflow/gateway/config/GatewayIamPublicJwkSource.java`：按契约解开 `data` 信封后再解析；为纵深防御同时容忍裸 JWK Set；未知或缺失 `kid` 一律失败关闭；文档读取有 2s 超时与 256KiB 上限；公开密钥缓存 300s（对齐契约 `maxCacheSeconds=300`），并发刷新单飞合并。
- `GatewayConfiguration` 的 JWT 解码器改用 `withJwkSource(publicKeys::select)`。
- 新增测试 +13：`GatewayIamPublicJwkSourceTest` 10/10；`GatewayEnvelopedJwksAuthenticationProcessTest` 3/3（真实 HTTP 信封 JWKS + 生产解码器验签通过并到达 owner 路由、同路由无令牌仍 401、未发布密钥签名的令牌 401）。
