## 目标与退出条件

把现有事件候选重整为 Phase 1 唯一、可生成、可校验并可做兼容比较的 Kafka + AsyncAPI D2 目录。退出前必须同时满足：

1. 每个目录条目具有唯一状态、event name/version、payload schema 和兼容策略；每个 `CANONICAL_D2` 事件还必须具有唯一 producer、data owner、consumer、consumer group、topic 与 aggregate partition key。无法证明这些绑定的条目必须保持 `HISTORICAL_CANDIDATE`，不得用默认值补齐或进入 AsyncAPI；未知或重复归属失败关闭；
2. canonical 事件只承载跨服务集成事实，前端/UI telemetry、日志、指标、同步 RPC、命令和数据库复制不得伪装成领域事件；
3. AsyncAPI 3.x 为每个 canonical 事件生成确定的 channel、publish/send operation、subscribe/receive operation和 Kafka binding，生成结果可复现且无手工漂移；
4. RabbitMQ 只允许标记为 `core-api` v1 historical compatibility，Redis/Redis Streams 明确禁止成为 v2 事件事实源；
5. envelope、敏感字段禁止表、schema version 与兼容窗口形成机器约束；破坏性 payload 或治理字段变更必须被真实 Git baseline comparison 拒绝；
6. 专项正反例、现有 P1R/契约生成与兼容回归、独立终验全部通过，且静态输出明确保持 `NOT_RUNTIME_VERIFIED`。

## 当前治理模型

- `catalog.json` 是状态与治理绑定的唯一事实源；其 `fragmentInventory` 双向冻结 14 个 event fragments 及每个文件的有序事件名，删除、重复、未知文件和顺序漂移均失败关闭。fragments 只提供事件/payload 语义，禁止再携带 `status`、`x-p1r-governance`、`x-kafka` 或手工 AsyncAPI。
- 当前 154 个条目全部显式分类：7 个 B26 workflow reliability 事件为 `CANONICAL_D2`，147 个尚未完成业务 owner/consumer 签收的条目为 `HISTORICAL_CANDIDATE`，`DEPRECATED=0`。这不是把 147 个候选判为废弃，而是阻止它们在对应 M1-008…017 完成前伪装成正式 Kafka 合同。
- canonical AsyncAPI 由 catalog 治理记录确定性生成：7 个 channel、7 个 `send` operation、14 个 `receive` operation；producer/data owner、consumer group、topic、partition key、payload ref 与 Kafka binding 必须精确一致。
- 共享信封契约 ID `platform.event.v1` 与每条事件的 `event.schema` 分开生成；每个 TypeScript 事件接口保留自身 schema 字面量及必填 `schemaVersion`，不能被信封 ID 覆盖。
- 16 个 `EVENT-GAP`/绑定族仍以 `PLANNED` closure registry 映射到领域契约任务和 M1-018 总 Gate；M1-006 只完成治理机制与已签收 seed，不提前关闭这些业务缺口。
- 所有输出仅为 `D2_CONTRACT_READY` / `NOT_RUNTIME_VERIFIED`。B26 继续是 `static-only`、`runtimeStatus=pending`、`defaultDecision=NO-GO`。
