# P1R-M2-004 — 独立 schema、Flyway、凭据、Redis namespace 与 tenant guard

状态：`IN_PROGRESS`

追溯：`ARCH-DATA-001`；依赖 `P1R-M2-003`（已 `ACCEPTED`）。Owner：各领域 Data Owner + `audit-service`。资产策略：`REUSE-VERIFY/REPAIR`。

## 1. 任务目标与最小退出证据

为每个数据 owner 落实独立 schema、可重复 Flyway 迁移、独立凭据与最小写权限、Redis namespace 隔离与 tenant guard，并覆盖 `audit-service`。

最小退出证据（台账口径）：
1. MySQL **空库**与**存量库**迁移均可重复执行（含 `audit-service`），`flyway_schema_history` 与声明一致，失败可恢复。
2. 每个 owner 使用独立 schema 与独立凭据；跨 schema 写入被数据库层面拒绝（非仅源码文本扫描）。
3. 跨租户读写阻断有真实 MySQL 测试（A 租户不得读/写 B 租户行），回滚/补偿路径可验证。
4. Redis 按服务 namespace 隔离（无共享键前缀依赖）。

范围边界：Kafka/Outbox 事件运行时（M2-005）、Saga/durable audit 摄取（M2-006）、可观测（M2-007）、全栈编排与 NetworkPolicy（M2-008）不在本任务内；`audit-service` 本任务只要求 schema/凭据/迁移与最小 ingest 边界，不做完整后台。

## 3. 实施方案（批次）

- **Batch A（阻塞解除：audit-service）**：创建 `services/audit-service` 骨架（端口登记同步 `config/local-ports.json`/`.env.example`/compose 说明）、`V1__create_audit_service_schema.sql`（append-only + legal-hold + receipt）、独立凭据与 Flyway 装配、`/internal/v1/audit/*` 最小 ingest 边界（fail-closed，禁止内存冒充持久）；Gateway ingest 消费者留至 M2-006，但契约与端口在本批固定。同步 `config/b17-runtime-services.json` 与 data-ownership policy。
- **Batch B（迁移可运行性）**：commerce 补 Flyway 依赖与程序化装配；统一“空库由外部 grant 预建（去 `createSchemas(true)`）/ 存量库 baseline”两路径；`scripts/database/reconcile-owner-schemas.mjs` 升级为按服务 Flyway 全量 + `flyway_schema_history` 校验；修正 `run-v2-services.mjs` 的死 Flyway env；产出空库迁移、存量升级、失败恢复三类运行证据。
- **Batch C（tenant guard 与阻断测试）**：先 learning/assessment 真实 MySQL 双租户交叉读写；再 content（SQL 加 tenant、消除 upsert 覆盖）、media（子表补 tenant_id、PK/查询带 tenant）、gamification（读加 tenant）、notification（去掉 `'unknown'` 默认）；随后 admin-ops/analytics/commerce/social；每服务至少“跨租户 0 行/403”与“跨 schema 写被 DB 拒绝”用例。
- **Batch D（凭据/Redis/最终证据）**：每服务独立口令与最小权限（去 CREATE/ALTER，schema 预建）；收敛 `svc_*` 与 policy 逻辑名；Redis namespace/ACL 落地（当前仅 Gateway 硬编码前缀），替换 b32 合成探针为真实缓存路径；按 data-ownership 8 项 runtime requirement 收集证据并升级 `runtimeStatus`，最后独立复审 → manifest → `ACCEPTED`。
