## 目标与验收

- 冻结 `notification-service` 对通知偏好、模板订阅、消息、投递结果和读回执的唯一事实边界；可信领域事件只通过显式 subscription/template/version/channel/locale/consent/dedupe 映射触发通知，偏好使用 expectedVersion/CAS 并包含分类、勿扰与频率政策；客户端、Gateway 和任意 BFF 均不得伪造领域事实或投递结果。
- 冻结通知失败的有界 retry、DLQ 与受控 recovery 契约；`workflow-service` 只拥有重试、DLQ、回放和人工恢复任务，通道失败不得回滚学习、支付、审核、客服或其他 owner 事实，关闭 recovery task 也不得替代 owner 对账。
- 冻结通用离线同步的共享有序协议、冲突投影和恢复入口：owner-specific canonical command 继续是唯一领域写入口，统一携带 `clientEventId/clientSeq/baseVersion/contentVersionId/payloadHash` 并按服务端 subject/device/aggregate 有序去重；客户端不是 Kafka producer，不得通过通用同步入口越过 SRS/attempt/权益/奖励等单一写边界。
- 冻结 `admin-ops-service.support` 对 ticket、message、assignment、SLA、resolution 与 retention metadata 的唯一所有权；learner `/api/v1/support/tickets*` 和 admin `/api/v1/admin/ops/tickets*` 允许角色化入口，但必须共享 ID、schema、状态机、幂等、expectedVersion/CAS、assignment/SLA history、错误和 owner。
- 冻结工单状态 `OPEN/ASSIGNED/WAITING_USER/WAITING_INTERNAL/RESOLVED/CLOSED/REOPENED`，七类最小分类、服务端派生 priority/assignment/SLA、最小脱敏上下文、受扫描附件、受限自由文本引用、保留/法律保留和敏感访问审计；support 不得直接修改订单、权益、学习、身份、内容或奖励事实。
- 建立 canonical OpenAPI、notification/sync/support v2 事件、AsyncAPI/B26 static binding、generated TypeScript、source-bound compatibility、专项 checker 与对抗测试；只在全部静态证据和独立终验通过后关闭 `CONTRACT-GAP-INF-001/002`、`CONTRACT-GAP-SUPPORT-ROUTING` 和 `EVENT-GAP-BIND-NOTIF-001`。
- 所有结论只能是 `D2_CONTRACT_READY` / `NOT_RUNTIME_VERIFIED`；B26 保持 `static-only/pending/NO-GO`，M6 与 M8 的真实实现、浏览器和 E2E 责任不提前完成。

## 冻结冲突处理

- B12 `/api/v1/notifications/*` 作为 notification canonical 路径候选；B11 `/api/v1/settings/notifications`、`/api/v1/messages*` 仅作 historical adapter，不允许两套通知事实并行晋升。
- Phase 1 canonical channel 必须覆盖 `IN_APP/PUSH/EMAIL/SMS`，但 SMS 仅允许验证码、登录安全、手机号换绑和极重要账户/支付状态等精确安全/必要交易模板；学习催促、营销和未知类型不得回退到 SMS。安全/必要交易与可选/营销通知采用不同 policy class，不能用一个总开关绕过法律、同意、退订或服务必要性边界。
- B11/B3/B4 的离线模型与 M1-013 单一 SRS 写入口有冲突；M1-016 不新增第二个 generic domain writer。旧 `/api/v1/sync/changes` 任意实体写入只作 historical candidate，canonical owner command 必须保留自己的 PEP、版本、幂等和状态转换，统一同步层只承载受控传输、冲突可见性和恢复引用。
- B5 learner support 与 B13 admin support 的状态、分类、message、assignment、SLA 和 retention 不一致；两组 v1 schema/event 只作 historical input，新 canonical 模型以 ADR-0014 与 Phase 1 业务运行设计为准，不依赖 merge 顺序覆盖。
- 旧 `support.ticket.created.v1` 存在重复 payload，通知与同步 v1 也有命名漂移；新集成事实使用具名 v2 event，禁止 dual publish、隐式 v1 promotion 或从 Java/B26 runtime candidate 推断 producer/consumer。
- S1 15 分钟确认/2 小时缓解和普通工单一个工作日首次回复只是待运营/合规确认的初始配置目标，不是公开 SLA 或 runtime PASS；契约只冻结版本化 SLA policy/reference、dueAt/state/escalation 语义。
- 客服描述、消息、截图和附件采用“受扫描的限制访问内容引用 + SHA-256 摘要 + redaction/scan/object version + 最小 safe preview”的正式口径；原始自由文本、URL、对象字节、Token、支付凭证、答案或音频不得进入事件、普通日志、receipt 或审计。精确保留期限不在本任务擅自填写，只冻结 retentionPolicyRef/version、retentionUntil、legalHoldState、owner/audit/reconciliation receipt 与失败关闭。
