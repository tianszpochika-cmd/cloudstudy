## 1. 这份计划取代什么

本目录是下一轮 Phase 1 开发的唯一执行计划。它以 [v2-980plus 设计包](../../../docs/06-design/v2-980plus/README.md)、[Phase 1 业务运行设计包](../../../docs/06-design/v2-980plus/phase1-business-operation/README.md)、[v2 微服务架构](../../../docs/02-architecture/v2-microservices-architecture.md)和 ADR-0009/0010/0012/0013/0014 为输入，从业务旅程、事实所有权和验收 Evidence 重新编排任务。

旧 B7–B36、旧 `DEV-*` 和旧 G0–G4 台账继续保留，但只用于以下用途：

- 说明已有代码、契约、脚本或历史运行证据可能可以复用；
- 解释迁移来源、历史决策和已知风险；
- 为新任务提供 `historical-candidate` 线索。

旧任务状态不得直接转换成新任务的 `ACCEPTED`。历史交接的 `LOCAL-TEST-NO-PASS` 仍用于说明没有可继承的运行完成结论；任何旧证据只有在当前提交、当前环境、当前契约和本计划 Evidence manifest 下重新验证后，才能成为新任务证据。

## 3. 编号、状态与成熟度

任务编号格式为 `P1R-M<里程碑>-<三位序号>`。`P1R` 表示 Phase 1 Rebaseline，明确区别于旧 B 批次和旧 `DEV-*`。

台账使用英文机器状态，但不改变 ADR-0007 的 canonical 中文状态；两者一一对应：`PLANNED=未开始`、`READY=已认领`、`IN_PROGRESS=进行中`、`REVIEW=待验收`、`ACCEPTED=已完成`、`BLOCKED=阻塞`、`REWORK=返工`。

台账另含 **「资产验证」列**（位于状态列之后），用于登记旧资产在 v2 架构下的可用性判定，取值：`不适用`（纯新建）/ `未验` / `已验-可用` / `已验-需修` / `已验-不可用`。适用于资产策略含 `REUSE-VERIFY` / `REPAIR` / `REWRITE` 的任务；其进入条件见 [01-里程碑与依赖图 §3.1 资产预检门](01-里程碑与依赖图.md)，验收口径见 [03-阶段验收与Evidence标准 §8](03-阶段验收与Evidence标准.md)。

允许的任务状态只有：

```text
PLANNED → READY → IN_PROGRESS → REVIEW → ACCEPTED
              ↘ BLOCKED        ↘ REWORK
```

| 状态 | 含义 | 必需证据 |
|---|---|---|
| `PLANNED` | 已进入计划，但依赖或进入 Gate 未满足 | 任务行完整 |
| `READY` | 依赖、范围、owner、契约输入和执行环境已确认 | G0 与适用的上游 Gate |
| `IN_PROGRESS` | 已由执行者认领并开始修改 | 认领记录、基线提交、文件边界 |
| `REVIEW` | 实现者认为交付物完成，等待独立验收 | 完整 Evidence manifest |
| `ACCEPTED` | 统筹/评审已按本计划验收 | 适用 Gate 全部 PASS |
| `BLOCKED` | 外部依赖、决策或环境阻塞 | 阻塞事实、owner、解除条件 |
| `REWORK` | 验收失败，需要返工 | 失败证据和返工范围 |

成熟度沿用业务运行设计的 D1–D5：

- `D1`：运行设计完成；当前基线已达到。
- `D2`：OpenAPI/AsyncAPI/schema/migration/policy 一致，Contract/Event GAP 关闭。
- `D3`：代码、生成物、单元/契约/最小集成测试通过。
- `D4`：真实 Gateway→owner DB→Outbox/Kafka→consumer→页面/Audit Evidence 通过。
- `D5`：安全、灾备、staging、不可变 RC、回滚和 Go/No-Go 通过。

## 4. 执行铁律

1. 严格按 [依赖图](01-里程碑与依赖图.md)和任务 `Depends On` 执行；不得因为某个目录已有代码就跳过 D2。
2. 每个任务必须绑定 `FEAT/PRD-ATOM/V2-980 + ARCH + ACT/JNY/PAGE/RULE/INT/E2E` 中适用的标识；没有业务标识的平台任务也必须绑定 `ARCH-*` 和受影响的 `INT/E2E`。
3. 坚持 `Contract/Data/Security first`：API、事件、数据、权限和状态机必须先完成契约，再修改服务与客户端；客户端不得手写未经验证的领域事实。
4. 旧代码先审计再决定 `REUSE-VERIFY`、`REPAIR`、`REWRITE` 或 `NEW`，不得按旧任务的“完成”标签盲目保留或删除。
5. 每个业务切片同时完成相关页面八态、服务侧 PEP、幂等、恢复和最小集成测试；不能把所有 UI、权限或异常处理留到最后。
6. `INT-P1-017` 的 Outbox、DLQ、重放和人工恢复是所有异步链路的共同前置，不是发布前临时补丁。
7. 生产支付始终默认关闭；本计划只允许激活码和支付 sandbox 形成可验收能力，生产渠道启用必须另行审批。
8. Phase 2 AI/实时语音和 Phase 3 K12 保持禁用、隔离和不可达；目录或占位代码不能进入 Phase 1 路由。
9. 时间估算不写入权威任务状态。执行者可在资源明确后生成迭代日历，但不得用日期替代依赖和 Gate。
10. 任务只能由实现者提交到 `REVIEW`，由独立统筹/评审依据 Evidence 改为 `ACCEPTED`。

## 5. 在另一台电脑开始执行

另一台电脑应从远程 `dev` 获取本计划所在提交，然后先执行 M0，不直接启动历史 B 批次。最小启动顺序是：

```text
同步 dev
  → 核对基线提交与工作区
  → 执行 P1R-M0-001…008
  → M0 Gate PASS
  → 执行 M1 Contract Ready
  → 只有 M1 Gate PASS 后进入实现里程碑
```

本机与另一台电脑的 JDK、Node、Docker、数据库或凭据差异应由 M0 记录并修复为可重复工具链；不得把本机环境差异写成业务需求或擅自降低目标技术栈。

## 6. 计划变更

- 任务拆分可以新增子任务，但原任务 ID 不重用、不重编号；父任务保留追溯和关闭条件。
- 改变范围、服务/data owner、技术主线、合规边界或不可逆迁移必须先更新设计/ADR，再改本计划。
- 仅修正文案、证据路径或依赖引用时，可以更新计划版本并在 `CHANGELOG.md` 留痕。
- 任何新增任务必须同步更新 [追溯覆盖矩阵](04-追溯覆盖矩阵.md)和计划校验器。
