# G0–G4 治理门禁任务基线

> 基线用途：把 DoD 的 G0–G4 从规范文本落实为可复现的代码化检查、边界测试和证据交接。
>
> 本基线是横切治理任务，不新增业务 Feature，不扩大 Phase 1 范围，也不替代 B0–B22 的运行态验收。

## 1. 任务范围

| Gate | 任务 ID | 主题 | 主要证据 | 默认状态 |
|---|---|---|---|---|
| G0 | `G0-SCOPE-001` | Phase 1 范围、需求/设计/ADR/ARCH 追溯、冻结枚举与冲突治理 | manifest、静态 validator、边界测试、范围证据索引 | `BLOCKED`，运行签收待提供 |
| G1 | `G1-CONTRACT-DATA-001` | API/事件/数据 schema 单一事实源、迁移 owner、兼容和租户边界 | 契约/迁移扫描、生成与兼容结果、运行 schema diff | `BLOCKED`，运行证据待提供 |
| G2 | `V2-G2-IMPLEMENTATION-INTERACTION-001` | 四端实现与交互状态、错误恢复、i18n/主题/性能降级 | 源标记检查、交互测试、浏览器/设备回放 | `NO-GO`，运行证据待提供 |
| G3 | `G3-TEST-SECURITY-OBSERVABILITY` | 测试、安全、隐私、权限、观测和 Phase 1 AI 禁用 | 测试/扫描/trace/audit/告警证据 | `NO-GO`，运行证据待提供 |
| G4 | `V2-G4-REL-ROLLBACK-001` | 发布、兼容窗口、迁移/恢复、审批、回滚和维护交接 | 发布清单、不可变 artifact、恢复点、回滚演练、签字 | `BLOCKED/NO-GO`，运行证据待提供 |

## 2. 依赖与边界

```text
G0 ─┬─> G1 ─> G2 ─> G3 ─> G4
    └──────────────────────> B0–B22 当前 Phase 1 基线
```

- G0–G4 的静态 validator 只能证明源文件、规则和证据契约存在，不能把目录、合成夹具或静态配置升级为运行态完成。
- G1 不允许跨服务共享写表、跨服务 SQL join、客户端提交 tenant/owner/role 事实或以 Redis 代替唯一事实源。
- G2 必须覆盖 `Loading/Empty/Error/Permission/Recovery`、国际化 fallback、主题和 Ultra/High/Medium/Performance 降级。
- G3 必须默认拒绝、保留 requestId/traceId/OTel/audit 关联，并确认 Phase 1 不启用生成式 AI、实时 AI 或 K12 路由。
- G4 默认 `NO-GO`、流量关闭、不可变 digest、恢复点和命名回滚 owner；不得由静态任务自动执行生产动作。
- 真实运行证据只能由批准的外部 runner 注入，并必须绑定环境、源版本、artifact digest、时间、审计和回滚责任。

## 3. 统一执行

```text
pnpm test:g
pnpm g:static
pnpm g:bootstrap --require-runtime
```

`pnpm g:static` 依次执行 DoD strict 预检、B22 静态前置、G0–G4 测试和 validator、契约校验/生成/兼容、固定端口、运行配置与 B7+ 任务基线。`--require-runtime` 在 B22 runtime Gate 和全部 G 运行证据齐全前必须 fail closed；它不启动集群、不迁移数据库、不切换流量、不批准上线。

## 4. 完成定义

G0–G4 只有在对应静态测试、validator、契约/任务基线和 DoD strict 检查通过，且真实运行证据由独立角色复核后，才能标记为 `已完成`。本轮代码实现完成不等于 Phase 1 已上线。
