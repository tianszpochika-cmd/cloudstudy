## What remains unknown without owner-signed aggregate evidence

The current source supports the following narrow statement: **the inspected IAM registration and token issuance paths use UUID identity; inspected learner code still accepts opaque `prn_` values on token claims/subject and in the owner type.** It does not support the stronger claim that no older issuer ever signed an opaque subject, no historical token remains valid, or no learner database row contains an opaque owner.

Before a D3 default-deny or mapping decision, IAM and learner owners should provide a redacted, owner-signed inventory from controlled historical sources. It must classify official signed-token issuers/versions and durable owner-key populations separately from synthetic tests, seeds, mocks and fixtures; report source/version/time range and aggregate counts or appropriately keyed hashes; and contain no raw subject, token, identifier or database dump. If data access is unavailable or provenance cannot be distinguished, record the legacy status as unknown and keep compatibility OPEN. Do not infer absence from present source or empty unit-test coverage.

The source-only fixture facts are explicit: learner domain tests use `prn_learner00000001`, and the event test uses the same synthetic shape as scope/actor ([`LearnerDomainTest.java`](../../../../../services/learner-service/src/test/java/com/englishflow/learner/LearnerDomainTest.java#L47-L57), [`LearnerOutboxEventTest.java`](../../../../../services/learner-service/src/test/java/com/englishflow/learner/domain/LearnerOutboxEventTest.java#L21-L31)). Those strings prove acceptance of a test format, not official issuance or persisted owner facts. The current IAM source has no `prn_` occurrence in its main Java implementation; a bounded `rg` over IAM/learner main and test Java found the production regexes and these learner test fixtures only.

## Actor semantics and contract implications

The frozen event envelope requires an `actorId` string of length 1–64, and the M1-018 bootstrap payload requires `principalId` matching `^prn_[A-Za-z0-9._:-]{15,127}$`. The schema does not express equality among `actorId`, `aggregateId` and `payload.principalId` ([envelope](../../../../../packages/contracts/events/v1/catalog.json#L472-L529), [M1-018 payload](../../../../../packages/contracts/events/v1/fragments/m1-018-iam-v2.events.json#L59-L74)). `prn_` plus a lowercase UUID is accepted by that payload regex, but this syntactic subset does not create an approved identity mapping or new cross-field invariant.

For public registration, decide explicitly whether event `actorId` means (a) the unauthenticated requester, (b) the newly created principal acting after account creation, or (c) a system/workload actor. `SELF_REGISTERED_ADULT_CANDIDATE` describes the bootstrap reason, not who acted. Existing IAM registration audit records the created account as the audit subject; the learner event accessor uses an authenticated owner as actor. Neither is a canonical IAM registration-actor decision. The old Outbox proposal also leaves the `actorId`/`aggregateId`/`principalId` relation pending ([proposal, lines 6–15](../../../../../evidence/p1r/m2/P1R-M2-002/redesign/R1-002/outbox-proposal-4.md#L6-L15)). IAM, audit and event-governance owners must approve the meaning and representation before an event producer is implemented.

There is no need to widen the frozen `prn_` regex solely to encode `prn_` plus UUID. If the decision adds equality/actor semantics absent from the canonical contract, document and approve that semantic rule in the identity ADR and event mapping/task specification; update a formal contract only if an actual field shape or published compatibility changes. Candidate A already calls for a numbered-later identity ADR and unchanged frozen compatibility checks ([draft, lines 39–44](../../R1-002-next-round-plan/identity-decision-A-draft.md#L39-L44)).

## Recommendation for a narrow future implementation

The two current learner call paths demonstrate why any resolver change needs named source scope and direct tests. A safe behavior-preserving sequence would be:

1. Keep existing production behavior unchanged while a pure, local codec is reviewed: exact `prn_` + canonical UUID encode/decode with shared non-secret golden vectors and negative cases, without modifying `PrincipalId.toString()`, JWT issuance, controller wiring, storage schema or event producer. This could be a separately named D3 preparatory slice only after explicit owner/root authorization; its tests do not close legacy compatibility or identity conflict.
2. Before wiring that codec, agree one resolver for both actual paths. `sub` remains the verified primary identity. Decide whether the already-issued `owner_id` must be checked equal to `sub`, and treat any `principal_id`/`principalId` alias only as an equality assertion, never as a replacement owner. Reject conflict/malformed/unknown legacy values with the existing denial boundary; do not erase current role, platform tenant, permission, adult-gate, consent or other PEP checks.
3. Test through the actual profile factory/controller and the B25 and target-pin callers: UUID sub only; exact matching alias claims; each conflicting alias and owner_id; opaque historical mapping absent/approved/expired/revoked; tenant/eligibility rejection unchanged. Preserve present source behavior until the D3 decision explicitly approves the common resolver; use no real user IDs or token material in vectors.
4. Keep Outbox producer, consumer, migration, Kafka and registration-transaction implementation outside this codec-only slice. A pure mapping test or the existing synthetic learner event cannot be reported as IAM bootstrap delivery.

This recommendation is a future decision option, not authorization to start D3. The draft's unresolved legacy inventory, claim-source policy and anonymous actor meaning remain decision gates. No source, database, service, token, canonical contract, task status or prior mobile-document delta was changed during this review.
